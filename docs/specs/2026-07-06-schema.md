Archive Ledger Schema Canvas

Revision: 2026-07-06 (supersedes 2026-06-09-preliminary-schema.md)

Purpose

This canvas tracks the evolving SQLite schema for Archive Ledger.

The SQLite database is a materialized view of the canonical JSONL event stream. Derived tables must be rebuildable by replaying canonical events.

This revision incorporates the decisions in docs/specs/2026-07-06-schema-design-decisions.md.

Schema Principles

1. JSONL events are canonical.
2. SQLite tables are either derived (rebuilt exactly by replay) or local-operational (excluded from the replay invariant). Every table declares its tier.
3. Every derived row traces back to canonical events.
4. Object identity is BLAKE3.
5. SHA-512/SHA-256 hashes from git-annex are stored as alternate hashes.
6. Paths are references, not identity. file_refs are logical; physical sightings live in path_observations.
7. Locations are logical storage places. Every stored path resolves under its location's URI.
8. Devices, sites, and risk domains are first-class. Physical site placement lives on the device; locations carry site_id only when device-less.
9. Archive roots are path-on-device concepts, not host mount points.
10. Device mounts are host-specific observations.
11. Materialized state holds event-driven facts only. Verification freshness is computed at query time, never stored.
12. MVP is single-writer: only the primary catalog host mints events. Events carry host_id and seq is scoped to a stream_id so per-host streams can merge deterministically later.
13. A host is a device; host_id columns reference devices.device_id. actor_id is a free-text convention.
14. The schema should support CLI-first MVP and daemon later.

Table Tiers

Derived (rebuilt exactly by replay):

- events (mirror), objects, object_hashes, collections, file_refs, path_observations
- devices, device_mounts, device_site_history, archive_roots, sites, risk_domains, entity_risk_domains, locations
- object_locations, verification_results, quarantine_items
- policies, checkpoints, sqlite_snapshots
- git_annex_imports, git_annex_keys, external_indexes

Local-operational (not rebuilt by replay; free to churn):

- archive_meta, jobs, job_items, policy_status, policy_rollup

"archive_meta"

Tier: local-operational.

Description

Small key-value table for database-local metadata.

This table tells the SQLite database what archive it belongs to, which schema version it uses, and how far it has replayed the canonical event stream.

Proposed columns

CREATE TABLE archive_meta (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL
);

"events"

Tier: derived mirror. Prunable.

Description

Queryable SQLite copy of the canonical JSONL event stream.

Not the source of truth. Rebuilt from JSONL; used for fast audit queries, dashboards, debugging, and object timelines.

seq is scoped per stream. MVP has exactly one stream (single writer on the primary catalog host). Per-host streams can be added later; replay merges streams deterministically.

Pruning: payload_json (or whole rows) older than the last checkpoint may be dropped via config/CLI. JSONL remains canonical.

Proposed columns

CREATE TABLE events (
  stream_id TEXT NOT NULL,
  seq INTEGER NOT NULL,
  event_id TEXT NOT NULL UNIQUE,
  event_type TEXT NOT NULL,
  event_time_utc_ms INTEGER NOT NULL,
  event_time_text TEXT NOT NULL,
  actor_id TEXT,
  host_id TEXT,
  job_id TEXT,
  object_id TEXT,
  location_id TEXT,
  device_id TEXT,
  site_id TEXT,
  payload_json TEXT,
  previous_event_hash TEXT,
  event_hash TEXT NOT NULL,
  PRIMARY KEY (stream_id, seq)
);

CREATE INDEX idx_events_type_time ON events(event_type, event_time_utc_ms);
CREATE INDEX idx_events_object_time ON events(object_id, event_time_utc_ms);
CREATE INDEX idx_events_location_time ON events(location_id, event_time_utc_ms);
CREATE INDEX idx_events_device_time ON events(device_id, event_time_utc_ms);
CREATE INDEX idx_events_job ON events(job_id);

Note: payload_json is nullable only to permit pruning; freshly applied events always carry it.

Example record

{
  "stream_id": "stream_primary",
  "seq": 184220,
  "event_id": "evt_01jz8p1kh9x6s4v8q0k1",
  "event_type": "object_verified",
  "event_time_utc_ms": 1781042405123,
  "event_time_text": "2026-06-09T18:00:05.123Z",
  "actor_id": "archive-daemon",
  "host_id": "dev_primary_pc",
  "job_id": "job_verify_usb8tb_a_20260609",
  "object_id": "blake3:2c7f...",
  "location_id": "loc_usb8tb_a_photos",
  "payload_json": "{\"result\":\"ok\",\"bytes_read\":42391551}",
  "previous_event_hash": "blake3:a91e...",
  "event_hash": "blake3:7bd9..."
}

"file_refs"

Tier: derived.

Description

A purely logical filename/path pointing to an object.

Paths are labels/references, not identity. Multiple file references can point to the same object.

A file_ref is location-independent: two clones of the same repo produce one file_ref. Physical sightings of the path live in path_observations.

Unique on (collection_id, logical_path) among active rows.

Proposed columns

CREATE TABLE file_refs (
  file_ref_id TEXT PRIMARY KEY,
  collection_id TEXT NOT NULL,
  object_id TEXT NOT NULL,
  logical_path TEXT NOT NULL,
  original_name TEXT,
  path_state TEXT NOT NULL,
  first_seen_event_id TEXT NOT NULL,
  last_seen_event_id TEXT,
  removed_event_id TEXT,
  created_time_utc_ms INTEGER,
  modified_time_utc_ms INTEGER,
  observed_size_bytes INTEGER,
  FOREIGN KEY (collection_id) REFERENCES collections(collection_id),
  FOREIGN KEY (object_id) REFERENCES objects(object_id)
);

CREATE UNIQUE INDEX idx_file_refs_active_path
  ON file_refs(collection_id, logical_path) WHERE path_state = 'active';
CREATE INDEX idx_file_refs_path ON file_refs(collection_id, logical_path);
CREATE INDEX idx_file_refs_object ON file_refs(object_id);
CREATE INDEX idx_file_refs_state ON file_refs(path_state);

Example record

{
  "file_ref_id": "fref_01jz8p...",
  "collection_id": "photos",
  "object_id": "blake3:2c7f9f9a...",
  "logical_path": "photos/2024/05/IMG_1234.JPG",
  "original_name": "IMG_1234.JPG",
  "path_state": "active",
  "first_seen_event_id": "evt_01jz8n...",
  "last_seen_event_id": "evt_01jz8n...",
  "removed_event_id": null,
  "created_time_utc_ms": null,

"path_observations"

Tier: derived.

Description

Where a logical path was actually seen.

One row per (file_ref, location). Two clones of the same repo yield one file_ref and two path_observations.

For git-annex, observations point at the git_annex_worktree location, not the CAS.

Proposed columns

CREATE TABLE path_observations (
  file_ref_id TEXT NOT NULL,
  location_id TEXT NOT NULL,
  object_id TEXT NOT NULL,
  observed_path TEXT NOT NULL,
  state TEXT NOT NULL,
  first_seen_event_id TEXT NOT NULL,
  last_seen_event_id TEXT,
  removed_event_id TEXT,
  last_seen_time_utc_ms INTEGER,
  observed_size_bytes INTEGER,
  modified_time_utc_ms INTEGER,
  PRIMARY KEY (file_ref_id, location_id),
  FOREIGN KEY (file_ref_id) REFERENCES file_refs(file_ref_id),
  FOREIGN KEY (location_id) REFERENCES locations(location_id),
  FOREIGN KEY (object_id) REFERENCES objects(object_id)
);

CREATE INDEX idx_path_obs_location ON path_observations(location_id, state);
CREATE INDEX idx_path_obs_object ON path_observations(object_id);

state values: present / removed.

observed_path is relative to the location's URI and must resolve under it.

Example record

{
  "file_ref_id": "fref_01jz8p...",
  "location_id": "loc_annex_photos_worktree",
  "object_id": "blake3:2c7f9f9a...",
  "observed_path": "2024/05/IMG_1234.JPG",
  "state": "present",
  "first_seen_event_id": "evt_01jz8n...",
  "last_seen_event_id": "evt_01jz8n...",
  "removed_event_id": null,
  "last_seen_time_utc_ms": 1781039200000,
  "observed_size_bytes": 42391551,
  "modified_time_utc_ms": 1715531200000

"devices"

Tier: derived.

Description

A physical or virtual storage-bearing entity.

Examples include primary PC, external USB drive, NAS, phone, server, or cloud account.

Physical site placement lives here: current_site_id holds present placement, updated by device_moved events. History lives in device_site_history.

"locations"

Tier: derived.

Description

A logical storage place where object bytes may exist.

A location may be a normal filesystem tree, git-annex worktree, git-annex CAS, future managed CAS, cloud location, or mobile ingest staging area.

A git-annex repo registers two locations: a git_annex_worktree location (repo root; path observations point here) and a git_annex_cas location (.git/annex/objects; object_locations and verification point here).

site_id is set only for device-less locations (e.g. cloud buckets). Device-backed locations inherit site through their device.

last_resolved_uri is a convenience cache. Resolution is always computed from device_mounts + archive_roots + relative_path.

"object_locations"

Tier: derived.

Description

Current materialized belief about whether a given object exists at a given location.

Holds event-driven facts only. Verification freshness (fresh vs stale) is computed at query time from last_verified_time_utc_ms against the governing policy's max_verification_age_days. Replay is therefore time-independent.

state values: present / missing / corrupt / quarantined / removed / unknown_offline.

Proposed columns

CREATE TABLE object_locations (
  object_id TEXT NOT NULL,
  location_id TEXT NOT NULL,
  state TEXT NOT NULL,
  first_seen_event_id TEXT,
  last_seen_event_id TEXT,
  last_verified_event_id TEXT,
  last_verified_time_utc_ms INTEGER,
  last_observed_path TEXT,
  last_error TEXT,
  quarantine_ref TEXT,
  PRIMARY KEY (object_id, location_id),
  FOREIGN KEY (object_id) REFERENCES objects(object_id),
  FOREIGN KEY (location_id) REFERENCES locations(location_id)
);

CREATE INDEX idx_object_locations_location ON object_locations(location_id, state);

Scale Expectations

At 1M objects across collections:

- objects ~1M rows; file_refs ~1M; path_observations and object_locations ~1 row per copy (~3M each at 3 locations). Comfortable for SQLite with the indexes above.
- Full replay of ~5-10M events rebuilds the database in minutes inside transactions; snapshots skip it.
- A yearly full verify pass of 1M objects x 3 locations mints ~3M object_verified events per year; compressed and git-packed, roughly 100-300 MB per year. Acceptable; see design-decisions doc for the manifest-based mitigation path if it ever hurts.

Resolved Questions (from the 2026-06-09 preliminary canvas)

All nine open questions from the preliminary canvas are resolved; see docs/specs/2026-07-06-schema-design-decisions.md.

Remaining Open Items

- Copy-destination layout convention (MVP 3): default direction is that filesystem_tree destinations mirror logical_path; detail when MVP 3 is designed.
- Event repo lifetime growth: fine for years at current volume; segment archiving is the future lever if needed.
- Canonical event vocabulary (event types and payload shapes) is not yet specced; that is the next design session.
