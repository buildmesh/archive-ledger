## Purpose

Archive Ledger is a local-first CLI for one person to inventory large personal archives, understand where every known file and copy resides, verify that stored bytes remain intact, and identify conditions that could cause permanent data loss.

The expected installation has one catalog owner. Its canonical history may be
replicated to a small number of the owner's enrolled installations, which can
temporarily diverge while offline and converge through the version 2 event-tree
protocol. It may track hundreds of thousands to millions of files across many
computers, removable drives, NAS devices, offline media, sites, and optional
cloud locations.

## Product outcomes

A user must be able to answer, without reading raw database rows or event files:

1. What files are known, including files whose bytes are not currently available?
2. Where is each known copy, and which device and site contain it?
3. When was each copy last observed and cryptographically verified?
4. Which copies are dependable under the applicable preservation policy?
5. Which files would become permanently unavailable after loss of a device, site, account, or shared dependency?
6. What uncertainty exists because a device is offline, a scan was partial, identity is unresolved, or verification is stale?
7. What safe, non-destructive action should the user take next?
8. How much canonical catalog history is locally checkpointed and independently replicated?

The product must never present an unverified, stale, unresolved, corrupt, missing, or ambiguously identified copy as proven protection.

## Scope and exclusions

### MVP scope

The MVP is a read-only preservation ledger over existing storage. It includes:

- archive, collection, device, site, root, location, risk-domain, and policy registration;
- device discovery and stable-identity confirmation where the platform exposes suitable identifiers;
- complete read-only import of supported git-annex repositories, including dropped or locally unavailable content;
- bounded, resumable location scans and checksum verification;
- per-file, per-object, per-copy, per-device, and per-location review commands;
- read-only policy and disaster-risk evaluation;
- loss-safe canonical event segments, SQLite projection, checkpoints, replication status, and clean-machine restoration;
- human-readable output and stable structured output from the same commands.

### Deferred scope

The initial read-only MVP did not mutate archive content. Current deferred scope excludes:

- automatic destructive cleanup;
- managed content-addressed storage writes;
- multi-user accounts, authorization, or roles;
- a background daemon or scheduler, including automatic targeted refresh of
  stale presence observations when removable devices appear;
- photo, document, email, search, OCR, face-recognition, or gallery features;
- per-file encryption or key management.

Repair, quarantine, and safe-drop operations may be added only after their safety contracts are
proven. Verified no-overwrite copy and narrow external-stage import are the implemented mutation
exceptions described below.

### Implemented post-MVP mutation scope

External-directory staging, its narrow import operation, and verified registered
Location-to-Location copy are implemented after the read-only contracts.
`archive stage PATH` is non-canonical and read-only with respect to the ledger.
`archive stage import SOURCE` may create new regular files only inside a newly
named subtree of a registered filesystem Location; it never overwrites, rewrites,
moves, or deletes existing content. `archive copy` creates verified destination
files without replacing existing paths and never changes its source.

## Operating model

### Normal reads

Normal review and reporting commands query SQLite only. They do not replay or scan canonical JSONL files. SQLite is the materialized current view and is the product's interactive query path.

### Mutations to catalog state

A catalog mutation writes a bounded batch to the local enrolled origin, closes
and signs its segment, advances a monotonic frontier, and then advances only that
origin's SQLite projection cursor. Incremental projection uses the stored
per-origin frontier and never rereads full history merely to discover unapplied
work.

### Synchronization and clone

Synchronization transports canonical metadata, not the content bytes stored in
Locations. It seals the local origin tail, fetches and validates missing
immutable origin segments, and publishes the verified union to one canonical Git
ref with compare-and-swap retry. Every synchronized installation retains the
complete accepted event tree; per-origin journals are merge-safe physical shards,
not separate ledgers. JSONL is never text-merged, SQLite databases are never
row-merged, and conflicts remain explicit catalog uncertainty.

An initial clone may install a verified portable SQLite snapshot supplied as an
out-of-band directory, bound to the
Archive ID, canonical Git commit, exact accepted frontier, schema version, and
projector version, then incrementally apply any newer ranges. The snapshot is a
non-authoritative cache outside canonical Git history and excludes credentials,
private client keys, local configuration, live mount-availability caches, and
unfinished local jobs. Canonical Device check-ins and mount evidence remain in
the projection. A missing, stale, corrupt, incompatible, or mismatched snapshot is
discarded without affecting canonical history; clone then performs a full rebuild.

### Explicit history operations

Full event-stream reads are reserved for:

- `archive events verify`;
- `archive fsck [--full]`;
- `archive db rebuild`;
- clean-machine restoration;
- explicit audit/history queries that cannot be answered by the SQLite mirror.

Full reads stream in bounded memory.

`archive fsck` is strictly read-only with respect to the selected Archive. Its
routine form runs strict Git object/ref verification, the authoritative signed
event/frontier verifier, SQLite `quick_check` and `foreign_key_check`, and
projection identity/cursor/currentness checks. It never applies, repairs,
checkpoints, commits, truncates, or replaces state. `--full` additionally
captures the live projection at one frontier, creates an isolated disposable
canonical clone and projection, and compares deterministic logical digests for
an exhaustive classification of event-derived tables. Local job/work queues are
excluded explicitly. A projection behind the current canonical tip is compared
at its captured historical applied frontier, while currentness remains a
separate actionable finding. The disposable rebuild passes SQLite
`integrity_check` and `foreign_key_check` and is removed by default;
`--keep-rebuild` and `--rebuild-dir` are explicit diagnostic controls. Exit 10
reports completed health/currentness findings, while exit 2 means a requested
check could not be completed.

## Domain model

### Archive and collection

An Archive is one named catalog, canonical history, policy boundary, and SQLite
materialized view owned by one user. It groups Collections but is not a file
tree, filesystem root, Device, or Location. Its storage directory is independent
of every directory it inventories.

A Collection is a logical namespace of File references, such as Photos,
Documents, or Email. A Collection may be represented partially or completely at
many Locations. A Location is not required to contain every Object in a
Collection, and completeness may be achieved only by the union of several
Locations on several Devices.

New Archives default to
`${XDG_DATA_HOME:-$HOME/.local/share}/archive-ledger/archives/<archive-id>/`.
The per-user configuration under
`${XDG_CONFIG_HOME:-$HOME/.config}/archive-ledger/` records known catalog paths
and the default Archive. This discovery configuration is local-operational and
recreatable; the Archive ID and display name are canonical. Existing explicitly
selected catalog directories remain usable and are never moved automatically.

Archive selection uses, in order: an explicit `--archive` selector, the
`ARCHIVE_LEDGER_ARCHIVE` environment variable, the configured default, or the
only known Archive. Ambiguous or missing selection fails with an actionable
error. Names are human selectors; stable IDs remain authoritative.

### Object

An object is a known byte sequence identified by `blake3:<lowercase-hex>`. A BLAKE3 object identity exists only after the bytes have been read successfully.

### External content identity

An external content identity is a source-system identifier such as a git-annex key. It can preserve knowledge of a file and its expected size or hash while its bytes are unavailable. It may later resolve to a BLAKE3 object.

An unresolved external identity is inventory, not a verified copy. It always remains visible and cannot satisfy a preservation policy.

Source-reported availability, such as a git-annex remote UUID claiming to have a
key, is also inventory rather than a copy. It is shown as a recovery lead until
the destination is mapped to catalog topology and the bytes are observed and
verified at a concrete location.

### File reference

A file reference is a logical path in a collection. It points to a known object, an external content identity, or both after resolution. Paths are references, not content identity.

Paths are lossless. Common UTF-8 paths are displayed normally; platform-native
paths that are not valid UTF-8 use an escaped display form and a lossless encoded
value in structured output. The encoded value, not the display rendering, is the
identity used for lookup and resume.

### Path observation

A path observation records where a logical path was seen, its representation, and the content identity it claimed at that time. Supported representations include ordinary files and the git-annex forms explicitly covered by importer fixtures.

### Copy claim

A copy claim is the catalog's current belief that content bytes exist at a specific path in a location. Claims can be present, missing, corrupt, unknown, or superseded by different content observed at the same path. A claim may refer initially to an external identity and later resolve to an object.

Multiple paths on the same device are multiple physical instances but not independent device-loss protection.

### Device, archive root, location, and site

- A device is a physical or virtual storage-bearing entity.
- An archive root is a filesystem or volume on a Device, identified internally
  and, when available, by stable filesystem evidence such as a filesystem UUID.
- A location is a logical storage area beneath a root, or a device-less service location.
- A site is a physical or logical place containing devices or service locations.

Host mount paths are observations, not Device or Archive Root identity. A
removable filesystem recognized by its UUID remains the same Archive Root when
mounted at a different path. Hardware fingerprints identify Devices when
available; filesystem or partition fingerprints identify Archive Roots. Because
identifiers can be absent or cloned, Archive Ledger retains internal stable IDs,
reports conflicts, and never treats an ambiguous match as independent storage.
A path mounted from an unexpected root or Device fails closed until the user
resolves the mismatch.

A Location path is stored relative to its Archive Root. For example, a root
currently mounted at `/var/data/sd01` and a repository at
`/var/data/sd01/annex/photos` produce the relative Location path
`annex/photos`. Changing the mount point does not change the Location.

MVP locations are either device-backed `filesystem` locations or device-less
`service` locations. A service is fully classified only with an active site,
trusted status, and known expected-availability class; encryption must also be
known when the policy requires it. Unknown or untrusted classification is shown
but cannot qualify.

### Risk domain

A risk domain represents a shared failure or dependency, such as a power circuit, chassis, account, provider, credential store, flood zone, or city.

Every device, every device-less service location, and every site is automatically
treated as a structural loss domain. The user does not need to create a custom
domain to learn what would be lost with a disk, service, or site. Custom risk
domains add shared dependencies that structural topology cannot infer.

## Trust and freshness model

Archive Ledger reports separate dimensions rather than collapsing them into one state:

- identity confidence: whether external identity has resolved to BLAKE3;
- existence claim: present, missing, corrupt, unknown, or superseded;
- observation freshness: age and completeness of the last covering scan;
- integrity freshness: age and result of the latest verification;
- device confidence: fingerprint match and check-in age;
- availability: online, expected offline, unexpectedly absent, or unknown.

### Qualifying copy

A copy qualifies as protection under a policy only when all of the following hold:

1. Its content has a BLAKE3 object identity.
2. Its current claim is `present`.
3. Its most recent verification succeeded, and no later missing, corrupt, identity-mismatch, or read-error observation invalidated that success.
4. Verification age is within the policy maximum.
5. Observation and device-check-in ages are within policy limits, including any explicit allowance for expected offline media.
6. Device identity is confirmed by a current match when online or a still-fresh
   prior match for expected-offline media. Unavailable or conflicting identity
   never proves device independence. A device-less service instead requires a
   fully classified service location.
7. Required encryption and trust properties are known and satisfied.
8. The collection, location, archive root (when applicable), device, and site are
   active and topologically consistent.

A non-qualifying claim remains visible as possible recovery material, with the exact reason it does not count.

## Scan semantics

A scan is a coverage claim, not merely a directory walk.

- A scan records its root identity, traversal rules, exclusions, start and finish times, counts, and errors.
- `complete` means the intended namespace was fully enumerated with no error capable of hiding entries.
- `partial` means interruption, permissions, I/O failure, device removal, unsupported representation, or another condition prevented full coverage.
- Observations made during a partial scan may add or refresh positive facts.
- A partial scan must never mark unseen paths or copies missing and must never refresh complete-coverage age.
- Missing transitions are emitted only after a complete scan compares the full observed set with the prior covered set.
- Missing transitions are provisional until one final `scan_completed` event
  validates their count and digest and marks the scan complete. Projection makes
  all of that scan's negative outcomes visible in the same SQLite transaction as
  the completion event. An interrupted or unfinalized scan can therefore add
  positive observations but cannot make anything missing.
- Expected exclusions are explicit and stable; changing exclusions produces a new coverage boundary.
- Concurrent filesystem changes are reported as uncertainty unless the source provides a stable snapshot.

The inventory scanner targets one registered location and collection, with an
optional logical-path prefix. It inventories ordinary regular files and hashes
new or identity-changed entries while streaming; the same successful read
records baseline verification for the resulting copy claim. Known entries whose
stable size/mtime metadata is unchanged refresh observation only; `archive
verify` performs routine rehashing. A content read/hash failure records the path
as present with unknown/non-qualifying identity and an integrity failure, but it
does not make namespace coverage partial. Traversal, directory-stat, or other
errors capable of hiding names do make coverage partial. Ordinary path handling
never follows symbolic links and rejects absolute or parent-scoped inventory
paths. The scanner never crosses the selected filesystem boundary, and the annex
adapter below permits relative parent components only when the normalized target
remains inside the registered object store. Symbolic links, special files, and
explicit exclusions are counted by category under versioned traversal rules;
they do not silently disappear. Every path component named `.git` is an automatic generic
traversal exclusion, including nested repositories and worktree marker files.
An unimported git-annex worktree is refused and directed to the annex importer.
After a completed import has registered that Collection and Location, the same
add and scan engine uses the materialized external identity and representation
facts to recognize annex paths without invoking Git or git-annex. It treats
dangling links and recognized pointer files as absent content, reads locked
content only through a target that passes both lexical and canonical containment
under the Location's `.git/annex/objects`, and hashes readable target bytes as
BLAKE3 plus the annex key's expected SHA-256. The object-store tree remains
excluded from generic traversal. A Git mode `120000` entry is annex-managed only
when its indexed target names the annex object store and valid key layout.
Every other symlink, including dangling and Git-tracked organizational links,
is counted as `ignored_symlinks`, is never followed, and emits no File, Object,
path-observation, Copy, or verification fact. Human annex-import, add, and scan
results state the ignored ordinary-symlink count; structured summaries expose
the same dedicated count. `ignored_non_annex` remains the inclusive annex-import
compatibility count.

Scan progress is local-operational and resumable. Durable observations and final coverage outcomes are canonical.

`archive collection add [path]` is positive, subtree-scoped inventory. It creates
or refreshes facts encountered beneath the selected path but never declares an
unvisited path missing and never advances complete-coverage freshness for a
larger Location. It uses the same scanner and event rules as a partial scan; it
is not a parallel inventory implementation.

`archive location scan [location]` is complete reconciliation of the registered
Location scope. Only its valid complete result may activate missing candidates
and refresh complete coverage. Both commands infer the Location and Collection
from the current directory when exactly one deepest registered match exists;
interactive ambiguity may prompt, while non-interactive ambiguity requires an
explicit selector.

## External-directory staging

`archive stage PATH [--collection COLLECTION]` audits an unfamiliar directory
without appending canonical events or changing the SQLite materialized ledger.
It streams same-filesystem traversal with the generic `.git`, symlink, special-
file, and containment rules, hashes stable regular files as BLAKE3, and compares
those identities against active File references in every Collection. A selected
Collection affects categorization only; a content match in any Collection means
the staged content is already cataloged and is ineligible for stage import.

Staging writes a versioned non-canonical SQLite checksum manifest under the
reserved `.archive-ledger-stage` directory when the source is writable. The
reserved directory is excluded from traversal. An explicit `--manifest` path is
supported; an unwritable source falls back to a private temporary manifest whose
path is reported. The manifest stores lossless relative paths, strong checksums,
stable metadata fingerprints, errors, audit generations, and the last derived
archive comparison. It is not an Archive, Location, Copy, or source of policy
evidence. Comparison is refreshed from current SQLite state without rehashing a
file whose size, modification time, inode, and change time still match.

For each cataloged staged Object, the command derives protection across every
active owning Collection from current usable policy-evaluation envelopes. It
reports staged-file counts as policy-satisfied, violated, or unknown; missing,
stale, incomplete, or unconfigured policy evidence is unknown. Staging does not
refresh the policy cache. `source_removal_ready` is true only for a complete
audit in which every stable regular file is cataloged and every active owning
Collection policy is satisfied by registered qualifying copies. The staging
source is never a copy or policy input.

`archive stage import SOURCE` runs from within a registered destination Location.
It infers Collection and Location where unambiguous, or accepts explicit
selectors. The destination is one new child subtree, defaulting to the staged
source name; an existing destination is a hard refusal. Dry run and explicit
non-interactive confirmation are supported. Only stable manifest entries whose
BLAKE3 is absent from every active Collection when the mutating job begins are
eligible. That reviewed selection is frozen in the non-canonical manifest for
the lifetime of the job so concurrent catalog additions cannot change resume
scope.

Import performs no standalone second source-checksum pass. It hashes each source
stream while writing a private destination-side tree and compares that result to
the manifest, syncs each temporary file, places it without replacing another
path, reads the placed bytes back, and requires the same checksum. Only after all
eligible entries succeed is the prepared tree atomically published. The source
is never changed. The published subtree is recorded through the authoritative
positive-only add scan, so canonical Object, File, path, Copy, and baseline
verification facts appear only for verified destination bytes. A changed source,
read failure, capacity failure, identity mismatch, path escape, or collision
publishes no final destination subtree and no content facts.

Import creates a durable local job before copying. Resume revalidates every
already prepared file against the frozen selection, continues missing files,
and refuses unexpected regular files, symlinks, special files, or checksum
mismatches. If a crash occurs after atomic publication but before the
positive-only add completes, resume may adopt that exact subtree only after the
same complete validation, then records the missing destination facts. Existing
unrelated destination trees are never adopted by a newly started job.

## Verification semantics

Verification reads bytes from a specific copy claim and computes the expected hash.

- Every attempted verification produces a canonical result: `ok`, `hash_mismatch`, `read_error`, or `identity_mismatch`.
- Verifying a present `unknown` claim establishes its BLAKE3 identity on a
  successful read and records that same read as baseline `ok` verification.
- Import-time hashing is verification and must be recorded as such.
- A hash mismatch makes that copy non-qualifying and corrupt; it does not silently change the expected object identity.
- A read error makes the copy non-qualifying until a later successful verification.
- Successful verification records the path read, bytes read, expected and observed hashes, duration, and device fingerprint confirmation.
- Verification jobs are bounded and resumable. Per-item progress may be local-operational, but each completed attempt is canonical.

## Policy and disaster-risk evaluation

The MVP deliberately has one applicable policy per collection rather than a
general selector language. `archive collection init` offers to create or reuse a
versioned starter policy, and each collection records its policy and home site.
The starter policy requires two
qualifying copies on two devices at two sites, including one site other than the
home site, with one-year verification, observation, and device-check-in limits;
it does not require an offline copy or encrypted offsite copy by default.
The user may update it before adding files. A collection without an active policy
or home site is `uncertain`, never compliant.

Risk reports use cached SQLite evaluations when current and automatically
recompute them from the SQLite materialized view when missing or stale. This
refresh never scans storage, reads canonical event history, or mutates archive
content. Explicit `archive policy evaluate` remains available for precomputation.
`archive policy update <policy>` accepts partial human-facing flags for copy,
Device, Site, offsite/offline/encryption, and evidence-age requirements; omitted
settings are preserved and every effective change creates the next policy
version through the normal full-snapshot event.

An offsite copy is a qualifying copy whose active site differs from the
collection's home site. A device-less service location must belong to a registered
logical site and otherwise follows the same rule. Policy versions replace their
predecessors; overlapping path selectors and precedence rules are outside the
MVP.

Unfiltered `archive status` and risk/policy reports evaluate every active
collection under its assigned policy and show unconfigured collections as
uncertain; a filter narrows that same result set rather than selecting a hidden
global policy.

Policies use a versioned, validated requirements object. The MVP supports:

- `min_qualifying_copies`;
- `min_devices`;
- `min_sites`;
- `require_offsite_copy`;
- `require_offline_copy`;
- `require_encrypted_offsite`;
- `max_verification_age_days`;
- `max_observation_age_days`;
- `max_device_checkin_age_days`.

Every requirements object contains every field: counts and age limits are
positive integers and `require_*` values are explicit booleans. Omission is an
error, not an implicit permissive default. Updating a policy writes a complete
new version.

`min_devices` counts distinct confirmed physical devices. A qualifying
device-less service copy contributes to copy, site, offsite, and service-loss
results, but it is reported separately and does not pretend to be a device.

Policy evaluation must:

- count independent devices and sites, not paths;
- use qualifying copies only;
- simulate loss of every device and site automatically;
- simulate loss of every device-less service location automatically;
- simulate every configured shared risk domain;
- include risk assignments inherited from location, archive root, device, and site exactly once;
- treat unknown topology, identity, encryption, or freshness as a visible violation or uncertainty, never as compliance;
- explain each failure using logical paths and human names;
- recommend a non-destructive next action such as verify a copy, connect a device, classify a location, or create an independent copy.

Reports include totals and bytes affected, support filters and pagination, and never hide additional failures behind a fixed sample limit.

Policy results may be cached for scale, but a cached result is usable only when it
covers the current applied frontier, policy-input generation, and policy version
and its `valid_until` time has not passed. The local policy-input generation
advances only for the exhaustive operation/item kinds that can affect file
policy or risk output; job, checkpoint, and metadata-replication bookkeeping
does not invalidate results.
`valid_until` is the earliest known freshness threshold crossing. Any mismatch
makes the result visibly stale/unknown and requires reevaluation; absence of a
violation row is compliance only inside a complete, still-valid evaluation.

## Canonical metadata protection

The canonical event stream is itself preservation metadata and must not depend on the catalog host surviving.

Archive Ledger's appended, projected, locally checkpointed, locally committed,
and independently replicated states name an exact frontier hash and canonical Git
commit rather than inventing a scalar sequence across origins. “Protected at
frontier F” requires a matching independently observed commit that contains F's
complete origin union. A local Git commit alone is not disaster protection in
either version.

Every metadata destination is a registered active location. It qualifies as
independent only when its structural storage domain (a device, or the service
location itself when device-less) and site differ from the catalog repository's
device and site and it shares no known custom risk domain with that repository.
Unknown topology is not independence. Local-path destinations are
resolved and fingerprint-checked so another directory on the same disk cannot be
mistaken for protection. Credentials remain outside canonical events.

The status report must show uncheckpointed and unreplicated tails. The MVP acceptance suite includes a clean-machine clone/restore, event-chain verification, and SQLite rebuild.

## Installation

The repository provides `make install` as the normal source-install path. It
checks for Cargo, Git, and a POSIX-compatible install utility and reports a
specific remediation when one is missing. It runs the locked release build and
installs `archive` beneath `${PREFIX:-$HOME/.local}/bin` by default without
invoking `sudo`. `PREFIX` and `DESTDIR` remain overrideable for packagers.
Git-annex itself is optional because the read-only importer uses Git metadata.
Git is required for the one-time annex import but not for subsequent inventory
of a registered imported Location. Commands that genuinely require an optional
executable detect it separately and explain the missing capability.

## CLI contract

Exact option spelling may evolve during implementation, but the following user jobs and command families are required.

Human-readable, concise, actionable output is the default. `--json` emits the
complete versioned structured result, and `ARCHIVE_LEDGER_OUTPUT=json` may set
that default once for an agent environment. Guided Archive and Collection setup
output omits storage implementation paths and stable IDs unless they are needed
for disambiguation; the structured result retains them.

### Setup and registry

- `archive init [<name>] [--name <name>] [--make-default]`
- `archive use <archive>`
- `archive rename <new-name>`
- `archive collection init|add|list|show|rename|update|retire|status`
- `archive site add|list|show|rename|update|retire|status`
- `archive device discover|add|list|show|rename|update|move|check-in|retire|status`
- `archive root add|list|show|update|retire`
- `archive location init|list|show|rename|update|retire|status`
- `archive risk-domain add|list|show|update|assign|unassign|retire`
- `archive policy add|list|show|update|evaluate|retire`
- `archive metadata-destination add|list|show|update|check|retire`

Registry corrections append replacement facts; they do not rewrite history.

`archive init` creates only a named Archive catalog and its local discovery
entry; it does not interpret the current directory or create topology. It
prompts for the name only on a terminal and requires positional `<name>` or
`--name` in non-interactive use. The first Archive becomes the default. Creating another preserves the
existing default unless `--make-default` is supplied.

`archive collection init` runs from the intended initial content directory by
default. It creates the Collection and initial Location, discovers the mounted
filesystem boundary, records the Location path relative to that root, reuses a
uniquely matching Archive Root and Device, and otherwise prompts for Device and
Site names unless supplied. When `--import-annex` is selected, it imports the
current repository as the first partial Location. Further repositories use
`archive location import-annex --collection <collection>` and may contain any
subset of Collection Objects. If the selected path is inside a detected
git-annex worktree, initialization without `--import-annex` fails before any
Collection or topology records are created. Likewise, `archive location init`
refuses an unimported annex worktree before topology changes and directs the user
to `location import-annex`. The import command reuses an active exact-root/path
Location left by an older client rather than creating a duplicate.

Filesystem/root discovery is evidence-based. A unique known filesystem UUID
reuses its Archive Root and Device without asking for aliases. New, unavailable,
or conflicting identity requires explicit confirmation; a mount path alone is
never silently promoted to stable identity. Display names default to
`<Collection> on <Device>` and are overrideable.

`rename` changes only a display name through the entity's existing full-snapshot
update event. Stable IDs, paths, relationships, and history do not change.
`archive device move <device> --to <site>` records a Site transition and
immediately invalidates affected cached risk results; it does not claim to move
physical media.

### Inventory and integrity

- `archive collection add [path]`
- `archive location scan [location]`
- `archive location import-annex [path] --collection <collection>`
- `archive annex-remote list|map|unmap`
- `archive verify`
- `archive job list|show|resume`
- `archive stage [path]`
- `archive stage import <source> [--dry-run|--yes]`
- `archive copy --to <location> [path ...] [--dry-run|--yes]`

Potentially long operations show progress on a terminal, are explicitly non-interactive when requested, and return a durable job ID.

`collection add` and `location scan` are thin entry points into one scan engine;
`location import-annex` is the one-time source-aware annex bootstrap. The scan
commands refuse an unimported git-annex worktree, but use the registered annex
facts and direct filesystem reads after import. These commands do not duplicate
hashing, coverage, resume, or event logic.

Human scan completion output distinguishes paths first added to the selected
Location from paths already known there, missing paths, and logical files whose
content was successfully hashed and integrity-verified during that run. It does
not label a refreshed path observation as a changed file. Structured output
retains `new_paths`, `changed_paths`, and `unchanged_paths` for compatibility and
adds `integrity_verified_paths`; `changed_paths` denotes replacement of an
existing path observation and is not a claim that byte identity changed. Human
output also reports `ignored_symlinks` when nonzero and makes clear that these
entries are not Archive Ledger Files.

The safe verified-copy mutation has two equivalent CLI entry points: `archive
copy` and `archive location copy`. Both dispatch to one implementation; the
top-level form is the concise normal workflow. The source Location and Collection
are inferred from `cwd` where unambiguous or selected explicitly. Positional paths
select logical Files or directory prefixes from SQLite; selection does not require
filesystem directory enumeration. Copy planning streams in stable order,
deduplicates selected Object identity, skips Objects already present at the
destination, and does not materialize ignored organizational symlinks as
redundant content.

Dry run performs the full database plan and read-only preflight. Before mutation,
copy confirms the registered identity of both mounted Devices, regular readable
source bytes for every selected Object, destination containment and nonexistence,
writability, and sufficient available capacity. It hashes each source stream
against the cataloged BLAKE3 while writing a same-directory temporary file, syncs
the file, publishes it with an atomic no-replace operation, and reads the final
destination back for the same checksum. A changed source, identity mismatch,
read error, capacity failure, containment failure, or collision is a hard refusal;
no existing destination or source is modified.
If the final read-back fails, the new unrecorded destination is left in place for
inspection rather than deleted; resume treats a mismatch there as a collision.

Copy has a durable local job record plus canonical job summaries and per-Object
observations. Projection is applied after each completed Object. Resume reconciles
already-recorded operation keys and verified destination bytes before continuing,
so a crash after publication cannot cause overwrite or duplicate canonical
outcomes. Policy satisfaction is not implied by a successful copy and remains a
separate risk evaluation.

### Review

- `archive status`
- `archive collection status [collection]`
- `archive location status [location]`
- `archive device status [device]`
- `archive site status [site]`
- `archive file find|show|history`
- `archive object show|history`
- `archive copy list|show`
- `archive report integrity|risk|policy|metadata|stale-presence`

Default output uses display names and logical paths. Object IDs remain available for precision but are not the only actionable identifier. `archive c`, `archive l`, `archive d`, and `archive s` are aliases for the Collection, Location, Device, and Site command families. `ls` aliases each family's `list`; human list output is one active display name per line, while `show`, `--all`, and `--json` expose detail as applicable.

`archive status` lists every active Collection with its logical File count and
current Policy violated and uncertain counts. Collection status reports its
name, logical File count, at-risk and uncertain totals, and every Location with
known inventory for that Collection; each Location row includes its Device,
Site, logical File count, present-byte total, and stale-presence count and
effective Policy age. Location status reports its Device, Site, path relative
to the Device root, logical File count, present-byte total, and stale-presence
count and age. Device status reports stable Device identity, current Site,
Location rows and their file/byte/stale totals, aggregate file/byte/stale totals,
and live physical free space when the currently mounted filesystem can be
revalidated against the registered Device identity. Site status lists its
Devices with aggregate file, present-byte, and stale-presence totals.

The versioned JSON forms retain detailed present, missing, corrupt, unknown,
unresolved, inventory, verification, policy, identity, and capacity status
needed by automation. Summary and report data query SQLite and never enumerate
a directory merely to answer a review request. Device free space is the sole
live filesystem statistic in these summaries; if mount availability or identity
cannot be proven, it is explicitly unavailable rather than sampled from an
unverified path.

File search is stable, lossless-path ordered, and bounded by an opaque
frontier-bound continuation. File show reports the exact current Copy count and
embeds at most 1,000 ordered Copy detail rows, with explicit truncation in JSON;
one heavily deduplicated Object must not create an unbounded response.

`archive report stale-presence` defaults to a concise Device list containing
each Device's deduplicated count of stale Objects. `--locations` shows indented
Location totals beneath each Device. Output prominently states the effective
period after which presence is stale and whether it comes from each applicable
Collection policy's `max_observation_age_days` or an `--older-than` override.
When policies differ, output shows the effective values or range rather than
inventing one global threshold. An Object is stale in the unfiltered report if
its latest positive observation exceeds at least one applicable active
Collection threshold; Device and Location counts deduplicate Object identity in
their respective scopes. Unresolved annex identities are reported separately.
Missing, corrupt, and integrity-stale copies are not mislabeled as stale
presence. The expanded form includes Site, expected availability, last complete
inventory, oldest observation, and the appropriate scan or annex-import action.

### Replication and synchronization

- `archive sync remote add|list|show|remove`
- `archive sync clone <remote> [--snapshot <directory>]`
- `archive sync enroll|approve|revoke`
- `archive sync [<remote>]`
- `archive sync status`
- `archive snapshot create [<directory>]`
- `archive snapshot inspect <directory>`

Every new Archive is initialized directly with a v2 genesis, initial enrolled
client, origin, frontier, Git commit, and schema-v6 projection. Pre-v2
development catalogs are rejected with instructions to recreate/import; there
is no in-place migration or mixed replay. A new client may read a clone
immediately but may not append until an existing enrolled client approves its
public key. Ordinary additive observations can then be made offline. Topology,
policy, client-registry, complete-scan negative publication, and future
destructive changes require a current coordination token. The initial product
uses one conservative Archive-wide scope; finer scopes are justified only if
real usage shows administrative concurrency needs them.

Human sync output names the remote, transferred immutable ranges, accepted
frontier, projection progress, conflicts, and whether a portable snapshot was
used. A successful sync means this installation has converged on the published
canonical frontier; it does not claim that content bytes were copied or that the
coordination remote is an independent metadata backup.

### Output and errors

- Human-readable output is the default.
- Every review/report command supports `--json` with versioned field names.
- Large lists support deterministic ordering, `--limit`, and a stable continuation mechanism.
- Routine SQLite continuation tokens bind to the query/filter version, applied
  frontier, and last sort key. Explicit File/Object history tokens instead bind
  the subject and match offset to the authenticated canonical frontier. If the
  relevant frontier advances between pages, the command returns
  `stale_continuation` and asks the user to restart instead of silently skipping
  or duplicating results.
- Mutations support explicit confirmation rules; no MVP command mutates archive content.
- Stable error codes distinguish invalid input, partial coverage, integrity failure, policy violation, device mismatch, lock contention, and damaged canonical history.
- Integrity and policy check commands use documented non-zero exit statuses when findings exceed the selected threshold.

Interactive setup commands offer prompts only for facts they cannot infer.
Every prompt has an explicit non-interactive flag equivalent; scripts are never
forced through prompts.

## Scale requirements

The design target is at least 500,000 file references and several million copy/observation facts on ordinary single-user hardware, with a path to one million files.

- Memory use is bounded by configured batches, not total files or events.
- Filesystem discovery streams; it does not collect and sort the entire archive in memory.
- Incremental projection reads only unapplied event lines.
- Rebuild reads the full event stream in bounded sequential passes; it never
  retains an Archive-sized decoded history.
- SQLite writes use prepared statements and bounded transactions. Complete-scan
  publication is the one intentional exception: its inferred coverage and
  negative set become visible in one set-based transaction so partial safety
  state is impossible.
- Reports operate from indexed projections and do not parse canonical payloads in their hot path.
- Scale claims must be supported by a reproducible 500,000-file fixture recording elapsed time, peak memory, database size, event volume, and resume behavior.

No fixed timing promise is made before measurement. A design that is superlinear in total event history is not acceptable.

## Acceptance scenarios

The MVP is not accepted until disposable fixtures prove:

1. Import of present, dropped, duplicate, unsupported, locked, and supported unlocked git-annex entries without repository mutation.
2. Inventory spanning at least three automatic event segments with contiguous manifests and a valid checkpoint.
3. Interruption and resume of import, scan, verification, and projection without lost or duplicated durable facts.
4. A crash after any subset of provisional scan-negative events, and a partial
   scan, cannot mark files missing or refresh full coverage; one valid completion
   activates exactly the declared negative set.
5. Import-time verification is visible as verification, and corruption/read errors prevent a copy from qualifying.
6. Two paths on one disk do not satisfy two-device protection.
7. Loss simulations for each disk, the home site, an account, and a custom shared domain identify affected logical files.
8. Unknown device identity, stale offline media, and unclassified risk remain explicit uncertainties.
9. Normal status, file, copy, and risk commands operate with the event repository unavailable but a current SQLite database present.
10. A clean machine restores the event repository from an independent destination, verifies it, and rebuilds the same derived state.
11. The 500,000-file scale fixture completes with bounded memory and linear event application.
12. A canonical job outcome appended before its local queue item is completed is
    reconciled on restart without emitting a duplicate outcome.
13. Policy results become stale/unknown after a relevant event, policy update, or
    freshness deadline rather than continuing to show compliance.
14. Duplicate device fingerprints, inconsistent root/location topology, and a
    metadata destination on the catalog disk cannot create false independence.
15. Non-UTF-8 fixture paths survive scan, event replay, SQLite rebuild, lookup,
    pagination, and structured output without identity loss.
16. The 500,000-file fixture exercises actual discovery/import and a complete
    policy evaluation, not only synthetic event projection.
17. An unchanged complete scan rebuilds identical per-fact coverage freshness;
    one unreadable file remains visible and non-qualifying without preventing
    missing detection for the rest of the fully enumerated namespace.
18. New-segment durability survives crash injection before and after event-file
    and parent-directory synchronization.
19. A removable filesystem imported at one mount point is recognized by stable
    root evidence at another mount point without creating a second independent
    Device; cloned or conflicting evidence fails closed.
20. Partial `collection add` refreshes only positive facts in its subtree, while a
    complete `location scan` alone can mark absent paths missing.
21. Cached Archive, Collection, Location, Device, Site, and concise
    stale-presence status remains fast with hundreds of thousands of files and
    does not enumerate storage. Device status may read filesystem capacity only
    after revalidating the mounted Device identity.
22. Generic inventories exclude `.git` paths. A detected git-annex worktree
    cannot be initialized through generic Collection or Location setup, and add
    or scan refuses it until a completed import has registered the Collection
    and Location; each refusal occurs before canonical state changes. Annex
    import reuses an already registered exact-path empty Location.
23. After that import, add and complete scan work with Git and git-annex
    unavailable, resolve newly readable annex content, detect content that later
    disappears (only the complete scan publishes that negative), never inventory
    `.git` as Collection files, preserve unsupported identities without treating
    them as corrupt copies, resume safely, and reject an annex symlink whose
    target escapes the registered object store without reading it. A mixed
    repository containing valid annex links plus ordinary and dangling
    organizational symlinks imports, adds, and scans only the annex-managed
    Files; ignored symlinks are reported and create no inventory or Copy facts.
24. External staging distinguishes archive-unknown, policy-violated,
    policy-unknown, and policy-satisfied content without changing ledger or
    policy state. Stage import resumes both a partially prepared tree and a
    fully published but unrecorded tree from its frozen selection, while source
    removal readiness remains false until every active owning Collection policy
    is satisfied by registered copies outside the staging source.
25. Two disposable enrolled installations add compatible facts while offline
    and converge, in either synchronization order, on the same canonical Git
    commit, complete origin set, accepted frontier, and projected state. A
    same-path/different-Object conflict remains visible; complete-scan negatives
    and registry edits cannot publish without their scoped token; JSONL is never
    text-merged and neither installation's accepted origin range disappears.
26. A clean clone validates and installs a portable SQLite snapshot, applies a
    newer multi-origin tail without full replay, and produces the same state as
    a clean rebuild. Corrupt, wrong-Archive, wrong-commit, wrong-frontier, and
    incompatible-schema snapshots fail closed without replacing a usable local
    database. Interrupted snapshot installation and incremental projection are
    recoverable.
