# Archive Ledger SQLite Schema Specification

Status: authoritative

Date: 2026-08-19

Schema version: 6

This document defines the logical SQLite model and projection invariants. It intentionally specifies required columns, keys, states, and indexes without freezing incidental SQL formatting.

Archive Ledger creates schema version 6 directly. Earlier development schemas
are rejected with a clear recreate/import instruction; no deployed-data or
mixed-event migration is supported.

## Principles

1. Canonical origin records/frontiers are authoritative; SQLite is rebuildable.
2. Normal product reads query SQLite only.
3. Tables are either canonically derived or local-operational.
4. Known byte identity is BLAKE3; unavailable bytes can retain an unresolved external identity.
5. A logical file, path observation, and physical copy claim are different facts.
6. Verification, observation freshness, device confidence, and online state remain separate dimensions.
7. Risk evaluation counts qualifying copies on independent devices/sites, not paths.
8. Structural loss of every device, device-less service location, and site is
   evaluated even without custom risk assignments.
9. Current-state projections retain origin dots and record references sufficient for audit navigation.
10. High-volume paths use bounded transactions, prepared statements, and indexed
    joins, except the single set-based transaction required to publish one scan's
    coverage atomically.
11. Path identity uses lossless platform-native bytes; escaped display text is
    presentation only.
12. A cached safety result is never trusted outside its declared frontier, policy,
    and time validity envelope.
13. A multi-origin projection has one applied cursor per origin; no scalar
    sequence imposes an arrival-order winner on concurrent facts.
14. SQLite databases from divergent installations are never merged row-to-row.
    A portable snapshot is an all-or-nothing cache bound to one accepted
    frontier, and later state comes only from canonical records.

## `archive_meta`

Key/value database-local metadata:

- `archive_id`
- `archive_display_name`
- `schema_version`
- `event_tree_version`
- `genesis_hash`
- `accepted_frontier_hash`
- `applied_frontier_hash`
- `item_projection_version`
- `projection_generation`
- `policy_input_generation`
- `last_verified_checkpoint_id`
- `last_verified_checkpoint_frontier_hash`
- `catalog_location_id`

Each changed per-origin cursor advances in the same SQLite transaction as its
projection rows. `policy_input_generation` advances only for exhaustive item
kinds that can affect file policy/risk output; job/checkpoint/replication
bookkeeping does not change it.
`catalog_location_id` is populated by `catalog_location_set` after the referenced
active device-backed location exists; it is not an unaudited path inferred from
the current process.
`archive_id` and `archive_display_name` are projected from canonical Archive
lifecycle records. Per-user catalog discovery and default selection are outside
SQLite and may be rebuilt without changing either value.

`accepted_frontier_hash` records the verified canonical Git tree offered to the projector;
`applied_frontier_hash` advances only when all of that frontier's causally ready
ranges and required batch completions have projected. Their inequality is
normal tail work, not corruption.

`projection_generation` is a database-local monotonic counter advanced with
each committed projection transaction. `policy_input_generation`
advances only when such a transaction changes a policy input. They support cache
and continuation invalidation but are not canonical time, do not synchronize,
and never choose between concurrent facts.

## `records`

Compact queryable mirror of canonical physical record headers:

```text
PRIMARY KEY (origin_id, origin_seq)
UNIQUE (record_id)

origin_id, origin_seq, record_id, record_kind, record_time_utc_ms
batch_id, causal_frontier_hash, segment_manifest_hash
previous_record_hash, record_hash
payload_json
```

Required indexes cover `(record_kind, record_time_utc_ms)` and
`(batch_id, origin_id, origin_seq)`.

One `batch_chunk` occupies one mirror row; items are not expanded into redundant
envelope rows. `payload_json` is nullable for format compatibility and is `NULL`
in a normal v2 projection. Batch context, completion state, operation outcomes,
and domain facts already have query-serving projections, while the immutable
canonical JSONL remains the authoritative payload for an explicit history read.
Duplicating a roughly 1 MiB scan chunk in SQLite would add no interactive-query
capability. Header rows remain for audit navigation and cursor validation.

### `projection_origins` (local-operational)

One row per origin known to the applied frontier:

```text
origin_id TEXT PRIMARY KEY
applied_seq INTEGER NOT NULL
applied_record_hash TEXT
applied_segment_manifest_hash TEXT
updated_time_utc_ms INTEGER NOT NULL
```

Sequence zero with null hashes represents an enrolled origin whose first record
has not projected. Advancing an origin cursor and all rows derived from those
records is one SQLite transaction. A frontier successor may add an origin but
may never omit or reduce an existing row. Proving an advanced manifest descends
from the stored cursor is an event-store responsibility performed before SQL
mutation.

## Multi-origin control and batches

These tables materialize canonical records; they do not create another
authority beside the event tree.

### `clients`

```text
client_id TEXT PRIMARY KEY                 -- origin_<64 lowercase hex>
display_name TEXT NOT NULL
public_key BLOB NOT NULL UNIQUE            -- Ed25519 public key
capabilities_json TEXT NOT NULL
status TEXT NOT NULL                       -- enrolled, revoked
approved_record_id TEXT NOT NULL
approved_origin_id TEXT NOT NULL
approved_origin_seq INTEGER NOT NULL
revoked_record_id TEXT
```

The projector checks that `client_id` is the specified digest of `public_key`.
The first accepted segment must causally follow enrollment. Revocation changes
future segment acceptance and never deletes accepted history. Private keys and
credentials have no column in this or any portable database.

### `batch_runs`

```text
batch_id TEXT PRIMARY KEY
origin_id TEXT NOT NULL REFERENCES clients
operation_kind TEXT NOT NULL
item_schema_version INTEGER NOT NULL
causal_frontier_hash TEXT NOT NULL
context_json TEXT NOT NULL
defaults_json TEXT NOT NULL
start_seq INTEGER NOT NULL
last_chunk_seq INTEGER
complete_seq INTEGER
item_count INTEGER NOT NULL DEFAULT 0
item_digest TEXT
state TEXT NOT NULL                       -- running, complete, invalid
negative_publication_state TEXT NOT NULL  -- none, pending, published
```

Chunk items project directly into the existing domain tables under versioned
rules and deterministic operation keys; no generic row-per-item JSON mirror is
required. This avoids recreating the storage duplication that batching removes.
For item schema 2, `defaults_json` is keyed first by item kind and then by field
name. Projection validates that shape, copies only the matching kind's defaults,
and overlays the explicit item. An explicit exception therefore wins over a
default; schema-1 items are projected without inheritance. The materialized
item is transient and is never stored as another JSON row.
Positive items may become current after their durable chunk. Complete-scan
missing candidates remain in `scan_missing_candidates` and are ineffective
until `batch_complete` validates ordered count/digest and publishes coverage in
one transaction. The projector rejects a complete record whose item count,
ordered digest, chunk ranges, or declared context does not match the start and
chunks already applied.

### `coordination_tokens`

```text
scope_kind TEXT NOT NULL
scope_id TEXT NOT NULL
token_id TEXT NOT NULL
holder_client_id TEXT NOT NULL REFERENCES clients
base_frontier_hash TEXT NOT NULL
state TEXT NOT NULL                       -- acquired, renewed, released, broken
not_before_utc_ms INTEGER NOT NULL
not_after_utc_ms INTEGER NOT NULL
last_record_id TEXT NOT NULL
PRIMARY KEY (scope_kind, scope_id)
```

This is the projected audit view of the signed coordination chain. The Git
compare-and-swap ref remains the publication rendezvous. A protected mutation
must name the current token and base frontier; projector validation is necessary
but does not replace publication-time ownership and expiry checks. The initial
implementation stores `scope_kind = archive` and the Archive ID as `scope_id`;
the schema retains explicit scope columns so a later, evidence-backed finer
scope does not require reinterpreting existing rows.

### Record references and causality

Every domain fact that needs audit identity stores its `record_id`, which joins
to `records` for the origin dot. Hot current-state rows that must compare
causality also store `state_origin_id` and `state_origin_seq` directly.
Uniqueness uses `(origin_id, origin_seq)`, never `origin_seq` alone.

Projectors compare version 2 facts as follows:

- a dot whose batch causal frontier includes the current dot may supersede it
  under that fact type's lifecycle rule;
- an identical additive fact coalesces while retaining its newest useful
  observation and verification evidence;
- causally concurrent compatible additions both remain effective;
- causally concurrent incompatible state, including different Objects for one
  logical path, creates explicit conflict rows/evidence and makes the affected
  Copy or File uncertain;
- physical projection order, record timestamp, origin ID, and Git merge-parent
  order never break a semantic tie;
- only a later fact whose causal base includes every conflicting dot may resolve
  that conflict.

`fact_conflicts` is the small generic index of unresolved
concurrent alternatives:

```text
conflict_id TEXT PRIMARY KEY
fact_kind TEXT NOT NULL
entity_key BLOB NOT NULL
left_origin_id TEXT NOT NULL
left_origin_seq INTEGER NOT NULL
left_record_id TEXT NOT NULL
right_origin_id TEXT NOT NULL
right_origin_seq INTEGER NOT NULL
right_record_id TEXT NOT NULL
state TEXT NOT NULL                       -- unresolved, resolved
resolved_record_id TEXT
UNIQUE (fact_kind, entity_key, left_origin_id, left_origin_seq,
        right_origin_id, right_origin_seq)
```

The projector orders the two dots lexically only to canonicalize this key, not
to select a winner. Domain tables retain their normal fast current-state rows;
an unresolved conflict changes the relevant state to `unknown`/conflict and the
alternatives remain recoverable through `records` and this index. A specialized
table should be added only if measured queries require more than this evidence.

Policy caches use `evaluated_frontier_hash`,
`evaluated_projection_generation`, and `evaluated_policy_input_generation`.
A cache is usable only at the same applied frontier and policy-input generation;
a local projection generation
may differ only when the intervening transactions are exhaustively classified
policy-irrelevant. Pagination tokens bind to `applied_frontier_hash` and
`projection_generation`.

Scan completion uses origin dots for candidate uniqueness and causal
comparison. Its negative candidates can supersede only facts included in the
scan's causal base and not refreshed by a descendant fact. A concurrent positive
observation therefore remains present or explicit conflict; it is never erased
because its origin sequence happens to be numerically lower.

Checkpoints and replication observations bind an accepted frontier hash plus its
canonical Git commit. Portable snapshot, metadata-protection, and status code
use that frontier binding.

## Content identity

### `objects`

One row per known byte sequence:

```text
object_id TEXT PRIMARY KEY                 -- blake3:<hex>
canonical_hash_algo TEXT NOT NULL          -- blake3
canonical_hash_hex TEXT NOT NULL UNIQUE
size_bytes INTEGER NOT NULL
media_type TEXT
extension_hint TEXT
first_seen_record_id TEXT NOT NULL
first_seen_time_utc_ms INTEGER NOT NULL
```

The projector verifies that `object_id`, algorithm, and hex agree.

### `object_hashes`

Alternate or source hashes attached to a resolved object:

```text
PRIMARY KEY (object_id, hash_algo, hash_hex)

object_id TEXT NOT NULL REFERENCES objects
hash_algo TEXT NOT NULL
hash_hex TEXT NOT NULL
source TEXT NOT NULL
verified_record_id TEXT
```

An index on `(hash_algo, hash_hex)` supports external lookup.

### `external_identities`

Source identities known before bytes are available:

```text
external_identity_id TEXT PRIMARY KEY
namespace TEXT NOT NULL                    -- e.g. git-annex
external_key TEXT NOT NULL
expected_hash_algo TEXT
expected_hash_hex TEXT
expected_size_bytes INTEGER
object_id TEXT REFERENCES objects          -- null until resolved
resolution_state TEXT NOT NULL
source_detail_json TEXT
first_seen_record_id TEXT NOT NULL
resolved_record_id TEXT

UNIQUE (namespace, external_key)
```

`resolution_state` is `unresolved`, `resolved`, `conflict`, or `unsupported`.

Resolution is monotonic from unresolved to resolved unless a later source conflict is observed. A conflict remains visible and prevents the identity from qualifying as protection.

### `external_availability`

Source-reported availability that does not identify an observed path:

```text
PRIMARY KEY (external_identity_id, source_repo_id, source_remote_id)

external_identity_id TEXT NOT NULL REFERENCES external_identities
source_repo_id TEXT NOT NULL
source_remote_id TEXT NOT NULL
state TEXT NOT NULL                         -- present, missing, unknown
location_id TEXT REFERENCES locations       -- null until explicitly mapped
observed_time_utc_ms INTEGER NOT NULL
observed_record_id TEXT NOT NULL
```

These rows are recovery leads, not copy claims, and never qualify as protection.
Mapping a remote to a location improves topology reporting but does not turn a
source assertion into observed or verified bytes.

`source_repo_id` is a stable source-system identity (the source annex UUID for
git-annex), not an import-run ID or host path; `source_remote_id` is the
source-reported remote UUID.

## Logical files and paths

### `collections`

```text
collection_id TEXT PRIMARY KEY
display_name TEXT NOT NULL
description TEXT
home_site_id TEXT REFERENCES sites
policy_id TEXT REFERENCES policies
status TEXT NOT NULL                      -- active, retired
last_record_id TEXT NOT NULL
```

Every active collection needs an active home site and policy for an evaluation
to report compliance. Missing or retired references produce `uncertain`.

### `file_refs`

A logical path's current content reference:

```text
file_ref_id TEXT PRIMARY KEY
collection_id TEXT NOT NULL REFERENCES collections
logical_path_bytes BLOB NOT NULL
logical_path_encoding TEXT NOT NULL
logical_path_display TEXT NOT NULL
object_id TEXT REFERENCES objects
external_identity_id TEXT REFERENCES external_identities
identity_state TEXT NOT NULL
path_state TEXT NOT NULL
created_time_utc_ms INTEGER
modified_time_utc_ms INTEGER
observed_size_bytes INTEGER
first_seen_record_id TEXT NOT NULL
last_seen_record_id TEXT
removed_record_id TEXT

CHECK (
  object_id IS NOT NULL OR external_identity_id IS NOT NULL
  OR identity_state IN ('unknown', 'conflict')
)
```

`identity_state` is `resolved`, `unresolved`, `conflict`, or `unknown`.
`unknown` represents an enumerated ordinary file whose bytes could not yet be
read; it remains visible and non-qualifying without inventing a content identity.
`path_state` is `active` or `removed`.

There is a partial unique index on
`(collection_id, logical_path_encoding, logical_path_bytes)` for
active rows, plus indexes on `object_id`, `external_identity_id`, and path
lookup. Path encoding is `utf8`, `unix_bytes`, or `windows_utf16le`; byte
identity is compared using binary collation within its encoding.
`logical_path_display` is escaped and must never be used as a key.

Keeping `external_identity_id` after resolution preserves provenance. An unresolved file reference remains a first-class inventory item and a policy violation; it is never silently omitted.

### `path_observations`

Current physical sighting of a logical path in a location:

```text
PRIMARY KEY (file_ref_id, location_id, observed_path_encoding, observed_path_bytes)

file_ref_id TEXT NOT NULL REFERENCES file_refs
location_id TEXT NOT NULL REFERENCES locations
observed_path_bytes BLOB NOT NULL
observed_path_encoding TEXT NOT NULL
observed_path_display TEXT NOT NULL
representation TEXT NOT NULL
object_id TEXT REFERENCES objects
external_identity_id TEXT REFERENCES external_identities
state TEXT NOT NULL
first_seen_record_id TEXT NOT NULL
last_seen_record_id TEXT
last_seen_time_utc_ms INTEGER NOT NULL
last_complete_scan_id TEXT
observed_size_bytes INTEGER
modified_time_utc_ms INTEGER
```

`representation` distinguishes ordinary files and supported source-specific forms. `state` is `present` or `missing`.

Observed paths are relative to their location and reject absolute forms, NUL,
and parent traversal. The platform adapter defines the lossless byte encoding;
case-folding or Unicode normalization is never assumed globally. Invalid UTF-8
fixtures are exercised end to end.

## Storage topology

### `sites`

```text
site_id TEXT PRIMARY KEY
display_name TEXT NOT NULL
site_kind TEXT NOT NULL
description TEXT
status TEXT NOT NULL
last_record_id TEXT NOT NULL
```

Every active site is an automatic structural loss domain.

### `devices`

```text
device_id TEXT PRIMARY KEY
display_name TEXT NOT NULL
device_kind TEXT NOT NULL
serial_hint TEXT
hardware_fingerprint TEXT
fingerprint_kind TEXT
identity_state TEXT NOT NULL
owner TEXT
status TEXT NOT NULL
current_site_id TEXT REFERENCES sites
expected_availability TEXT NOT NULL
last_checkin_record_id TEXT
last_checkin_time_utc_ms INTEGER
last_fingerprint_match_time_utc_ms INTEGER
last_fingerprint_status TEXT
last_record_id TEXT NOT NULL
```

Every active device is an automatic structural loss domain. `expected_availability` is `online`, `offline`, or `intermittent`; it does not itself assert current availability.

If the platform cannot expose a stable fingerprint, that uncertainty is stored explicitly. A known fingerprint mismatch blocks scan and verification until resolved.

`identity_state` is `confirmed`, `unavailable`, or `conflict`. A partial unique
index on `(fingerprint_kind, hardware_fingerprint)` for active devices with a
non-null confirmed fingerprint prevents one physical device from being counted
twice. Discovery of an existing fingerprint resolves to the existing device.
Cloned or conflicting fingerprints remain non-qualifying until the user supplies
a stronger identity or records the device as unconfirmed; the MVP does not invent
a second independent device from an alias.

Device fingerprint values are paired with a non-empty hardware evidence kind.
Confirmed and conflicting states require both values; `unavailable` stores
neither. Filesystem/partition UUIDs, labels, and mount paths are Archive Root
evidence and are rejected as Device hardware fingerprints. A confirmation also
records a `match` Device check-in; withdrawing or conflicting identity records
`unavailable` or `mismatch`, respectively, so Policy changes fail closed.

### `device_mounts`

Append-derived mount observations:

```text
mount_id TEXT PRIMARY KEY
device_id TEXT NOT NULL REFERENCES devices
archive_root_id TEXT REFERENCES archive_roots
host_id TEXT NOT NULL REFERENCES devices
mount_root_uri TEXT NOT NULL
status TEXT NOT NULL                    -- mounted, unmounted, mismatch
fingerprint_status TEXT NOT NULL
observed_time_utc_ms INTEGER NOT NULL
observed_record_id TEXT NOT NULL
```

Indexes on `(archive_root_id, observed_time_utc_ms)`,
`(device_id, observed_time_utc_ms)`, and `(host_id, observed_time_utc_ms)` support
latest-mount resolution. The projector requires every observation to name an
Archive Root belonging to the referenced Device; a null or inconsistent root
cannot establish current confidence.

### `device_site_history`

```text
PRIMARY KEY (device_id, arrived_time_utc_ms)

device_id TEXT NOT NULL REFERENCES devices
site_id TEXT NOT NULL REFERENCES sites
arrived_time_utc_ms INTEGER NOT NULL
departed_time_utc_ms INTEGER
moved_record_id TEXT NOT NULL
```

Exactly one open site interval may exist per active device.

### `archive_roots`

```text
archive_root_id TEXT PRIMARY KEY
device_id TEXT NOT NULL REFERENCES devices
display_name TEXT NOT NULL
filesystem_fingerprint TEXT
fingerprint_kind TEXT
identity_state TEXT NOT NULL
root_path_on_device_bytes BLOB NOT NULL
root_path_encoding TEXT NOT NULL
root_path_display TEXT NOT NULL
status TEXT NOT NULL
created_record_id TEXT NOT NULL
last_seen_record_id TEXT
last_seen_time_utc_ms INTEGER
```

The root path is relative to stable Device identity, not a transient host mount.
`fingerprint_kind` identifies evidence such as `filesystem_uuid` or
`partition_uuid`; it is distinct from Device hardware identity. `identity_state`
is `confirmed`, `unavailable`, or `conflict`. Registration and import validate
that a root belongs to the selected Device. Active roots are unique by
`(device_id, root_path_encoding, root_path_on_device_bytes)`. A partial unique
index on `(fingerprint_kind, filesystem_fingerprint)` for active confirmed roots
allows a removable filesystem to be recognized after its mount path changes.
Duplicate/cloned fingerprints enter conflict handling and never establish a
second independent Device automatically.

### `locations`

```text
location_id TEXT PRIMARY KEY
display_name TEXT NOT NULL
kind TEXT NOT NULL
archive_root_id TEXT REFERENCES archive_roots
relative_path_bytes BLOB
relative_path_encoding TEXT
relative_path_display TEXT
device_id TEXT REFERENCES devices
site_id TEXT REFERENCES sites
encryption_state TEXT
trust_level TEXT
expected_availability TEXT NOT NULL
is_writable INTEGER NOT NULL DEFAULT 0
status TEXT NOT NULL
created_record_id TEXT NOT NULL
last_record_id TEXT NOT NULL

CHECK (
  (archive_root_id IS NOT NULL AND device_id IS NOT NULL AND site_id IS NULL
   AND relative_path_bytes IS NOT NULL)
  OR
  (archive_root_id IS NULL AND device_id IS NULL AND site_id IS NOT NULL
   AND relative_path_bytes IS NULL)
)
```

MVP location values are closed and validated:

- `kind` is `filesystem` for device-backed locations or `service` for
  device-less locations;
- `encryption_state` is `encrypted`, `unencrypted`, or `unknown`;
- `trust_level` is `trusted`, `untrusted`, or `unknown`;
- `expected_availability` is `online`, `offline`, or `intermittent`.

Device-backed locations inherit site from the device, and the projector requires
`locations.device_id` to equal the referenced root's device. A device-less
service location uses `site_id`. Both forms therefore have exactly one topology
route; neither all-null nor mixed root/device combinations are valid. Current
resolved URIs and online state are computed from mount observations and registry
facts; they are not trusted as permanent identity.

Each active device-less service location is also an automatic structural storage
loss domain. It can satisfy copy and site requirements when otherwise qualifying,
but it does not masquerade as a physical device in device-count reporting.
A service location is fully classified only when it is active, has kind
`service`, references an active site, has trust level `trusted`, and has a valid
expected-availability value. Encryption must additionally be known and satisfy
the policy when an encryption requirement applies. `unknown` or `untrusted`
values remain visible but cannot qualify.

Required indexes cover device, site, root, kind, and status.

## Copy claims and integrity

### `copy_claims`

Current belief about one physical content instance:

```text
copy_claim_id TEXT PRIMARY KEY
location_id TEXT NOT NULL REFERENCES locations
relative_path_bytes BLOB NOT NULL
relative_path_encoding TEXT NOT NULL
relative_path_display TEXT NOT NULL
object_id TEXT REFERENCES objects
external_identity_id TEXT REFERENCES external_identities
claim_basis TEXT NOT NULL
state TEXT NOT NULL
state_origin_id TEXT NOT NULL
state_origin_seq INTEGER NOT NULL
state_record_id TEXT NOT NULL
first_seen_record_id TEXT NOT NULL
last_seen_record_id TEXT
last_seen_time_utc_ms INTEGER
last_complete_scan_id TEXT
last_verified_record_id TEXT
last_verified_time_utc_ms INTEGER
last_verification_result TEXT
last_error_code TEXT
last_error_detail TEXT

CHECK (
  object_id IS NOT NULL OR external_identity_id IS NOT NULL
  OR state = 'unknown'
)
```

`claim_basis` is `observed_bytes`, `observed_metadata`, or `source_metadata`.
`observed_metadata` represents an enumerated path whose bytes could not yet be
identified. Source metadata attached
to a concrete observed placeholder path is useful inventory but does not
qualify. Remote UUID/key availability without a path belongs only in
`external_availability`.

`state` is `present`, `missing`, `corrupt`, `unknown`, or `superseded`.
`quarantined` and `removed` are not reserved because the MVP has no operation
that can create them. There is one partial unique active-path index on
`(location_id, relative_path_encoding, relative_path_bytes)` where state is not
`superseded`.

Copy lifecycle is explicit:

| New durable fact | Current-state result |
| --- | --- |
| same identity observed at the path | `present`; an earlier successful verification remains dated evidence |
| complete scan finalizes absence | `missing`; any earlier verification stops qualifying |
| different identity observed at the path | old claim becomes `superseded`; a new unverified `present` claim is created |
| hash or identity mismatch | `corrupt`; earlier verification is invalidated |
| read error or device-identity failure | `unknown`; earlier verification is invalidated |
| later successful verification of the expected identity | `present`; failure fields clear and the new success becomes current |
| successful baseline read of an unknown claim | object/file identities resolve, state becomes `present`, and the baseline success becomes current |
| registry entity is retired | claim remains historical but cannot qualify while its topology is inactive |

A `copy_observed` identity replacement names the prior claim it supersedes, so
incremental projection and rebuild take the same transition. Source-metadata
claims are `unknown` and cannot become qualifying without a concrete byte
observation.

Indexes support `(object_id, state)`, `(external_identity_id, state)`, `(location_id, state)`, and verification age. Multiple claims on one device never inflate the independent-device count.

### `verification_results`

Historical attempt results:

```text
verification_id TEXT PRIMARY KEY
record_id TEXT NOT NULL
item_index INTEGER NOT NULL
job_id TEXT
copy_claim_id TEXT NOT NULL REFERENCES copy_claims
object_id TEXT REFERENCES objects
location_id TEXT NOT NULL REFERENCES locations
result TEXT NOT NULL
expected_hash_algo TEXT
expected_hash_hex TEXT
observed_hash_hex TEXT
size_bytes INTEGER
bytes_read INTEGER
duration_ms INTEGER
verified_time_utc_ms INTEGER NOT NULL
path_observed_bytes BLOB NOT NULL
path_observed_encoding TEXT NOT NULL
path_observed_display TEXT NOT NULL
device_fingerprint_status TEXT NOT NULL
error_code TEXT
error_detail TEXT
UNIQUE (record_id, item_index)
```

`result` is `ok`, `hash_mismatch`, `read_error`, or `identity_mismatch`.

All failures are retained in SQLite. Older successes may be pruned only behind a
verified replicated checkpoint while retaining the newest success per copy
claim. Canonical records remain complete.

The qualifying-copy predicate also joins active collection, location, root,
device, and site state. It does not rely on `copy_claims.state` alone.

## Scan coverage

### `scan_runs`

Canonical summary of each scan:

```text
scan_id TEXT PRIMARY KEY
job_id TEXT
location_id TEXT NOT NULL REFERENCES locations
collection_id TEXT NOT NULL REFERENCES collections
logical_prefix_bytes BLOB
logical_prefix_encoding TEXT
logical_prefix_display TEXT
status TEXT NOT NULL
scan_mode TEXT NOT NULL
started_time_utc_ms INTEGER NOT NULL
causal_frontier_hash TEXT NOT NULL
finished_time_utc_ms INTEGER
coverage_version INTEGER NOT NULL
scope_json TEXT NOT NULL
exclusions_json TEXT NOT NULL
exclusions_hash TEXT NOT NULL
observations_count INTEGER NOT NULL DEFAULT 0
observations_digest TEXT
missing_candidate_count INTEGER NOT NULL DEFAULT 0
missing_candidate_digest TEXT
files_seen INTEGER NOT NULL DEFAULT 0
bytes_seen INTEGER NOT NULL DEFAULT 0
new_paths INTEGER NOT NULL DEFAULT 0
changed_paths INTEGER NOT NULL DEFAULT 0
missing_paths INTEGER NOT NULL DEFAULT 0
unchanged_paths INTEGER NOT NULL DEFAULT 0
error_count INTEGER NOT NULL DEFAULT 0
error_summary_json TEXT NOT NULL
started_record_id TEXT NOT NULL
finished_record_id TEXT
```

`status` is `running`, `complete`, `partial`, `failed`, or `cancelled`.
`scan_mode` is `add` or `complete`. Only a successfully completed run whose
`scan_mode` is `complete` can populate `missing_paths` or become
`last_complete_scan_id` on covered facts. A completed `add` run may refresh
positive per-fact `last_seen_time_utc_ms` values but cannot publish negative or
complete-coverage facts.

Indexes on `(location_id, finished_time_utc_ms)` and status support freshness reports.

Detailed transient traversal errors live in job items or an external job log. Canonical completion retains stable counts and categories sufficient to explain why coverage was partial.

`scope_json` and `exclusions_json` contain the normalized versioned rules needed
for replay; the hash is validation/convenience, not a substitute for those rules.
Only one running scan may exist for the same location, collection, and normalized
scope. A causally concurrent path/copy item from another job forces partial completion.

### `scan_missing_candidates`

Canonically derived, inert negative observations waiting for scan finalization:

```text
candidate_id TEXT PRIMARY KEY
origin_id TEXT NOT NULL
origin_seq INTEGER NOT NULL
record_id TEXT NOT NULL
item_index INTEGER NOT NULL
record_hash TEXT NOT NULL
scan_id TEXT NOT NULL REFERENCES scan_runs
candidate_kind TEXT NOT NULL                -- path, copy
file_ref_id TEXT REFERENCES file_refs
copy_claim_id TEXT REFERENCES copy_claims
location_id TEXT NOT NULL REFERENCES locations
path_bytes BLOB NOT NULL
path_encoding TEXT NOT NULL
activated INTEGER NOT NULL DEFAULT 0
UNIQUE (origin_id, origin_seq, item_index)
```

Indexes on `(scan_id, origin_id, origin_seq, item_index)` and target IDs support streaming
digest validation and one set-based activation. Until `activated = 1`, candidates
are excluded from every current-state and freshness query. Projection of a valid
complete `batch_complete` record verifies the scope, count, and digest, then uses
set-based SQL to activate the candidates, update covered current facts, mark the
scan complete, and advance the affected origin cursor in one transaction.
The operation is bounded-memory even for a large missing set. Any validation or
SQL failure rolls the entire transaction back. Partial or unfinalized candidates
never activate.

The candidate's causal frontier is its ordering proof. Activation does not
overwrite a target whose current state was established by a concurrent or
descendant positive, replacement, or verification item; `missing_paths` distinguishes
candidates that became current from candidates superseded before finalization.

For a complete scan, the projector also infers the unchanged covered set from
canonically derived current facts: path state must be `present` and copy state must be
`present`, `corrupt`, or `unknown`; facts already `missing` or `superseded` are
excluded. Each remaining fact must be in the canonical scope/exclusions, have
existed in `causal_frontier_hash` or have been emitted by this scan, and not be made
missing by a newer effective candidate. It streams those stable keys to
recompute the completion event's observation count/digest and updates their
`last_complete_scan_id` in the same transaction. Rebuild uses exactly this rule;
local job staging is never an input.

The scanner maps each ordinary regular file's relative byte path to the selected
collection plus optional logical prefix. Its ordinary path handling rejects
absolute and parent escapes, does not follow symlinks or cross the selected
filesystem, and records versioned counts for symlinks, special files,
exclusions, and traversal errors. For a Location with a completed annex import,
the materialized `file_refs`, `external_identities`, `path_observations`, and
`annex_imports` rows select an annex-aware adapter without consulting Git. That
adapter may read a known locked symlink target only after lexical and canonical
containment beneath the Location's `.git/annex/objects`; the object-store tree
itself remains excluded from namespace traversal. Copy presence is keyed by the
validated Location-relative target path, while logical presence remains keyed by
the tracked Collection path. All other symlinks increment the run's dedicated
`ignored_symlinks` summary count and produce no durable File, path-observation,
Object, Copy, or verification row. Annex import also exposes that dedicated
count while retaining the inclusive `ignored_non_annex` count for structured
output compatibility.

## Non-canonical stage manifest

External staging adds no table to `archive.db`. Its versioned SQLite manifest is
stored under `.archive-ledger-stage/manifest.sqlite3`, at an explicit
`--manifest` path, or in a reported private temporary directory when the source
is unwritable. It contains:

- key/value metadata for schema version, source path, audit generation and
  completion, and the Archive ID/applied sequence used for the last comparison;
- one lossless relative-path row per observed regular file with size,
  modification time, platform metadata fingerprint, BLAKE3, content-read state,
  generation, and derived archive-membership state;
- one local import-job row binding a durable job ID to the audit generation and
  canonical source path, plus lossless path keys freezing the archive-unknown
  selection made when that mutating job began;
- indexes by generation/content state and checksum for bounded comparison and
  duplicate counting.

The manifest is cache and work product, not canonical history or materialized
ledger state. Rebuild never consumes it. Its membership classifications can be
stale and are recomputed against current `objects` plus active `file_refs`
before a new import job. Policy classifications are derived from complete,
current local policy-evaluation envelopes and are never treated as canonical
manifest facts. A resumed import uses its frozen selection rather than silently
changing scope after concurrent Archive mutations. Only destination observations
emitted after verified placement enter the canonical schema above.

## Verified copy persistence

Registered Location-to-Location copy requires no separate content-transfer table
in the materialized view. Planning streams active `file_refs`, `objects`, source
`copy_claims`, and destination presence in stable Object order. Successful
placement is projected through the existing `path_observations`, `copy_claims`,
`verifications`, operation-key index, and job tables. Therefore status and risk
queries see exactly the same evidence whether bytes arrived through scan, annex
import, stage import, or verified copy.

The local job parameters retain stable source, destination, Collection, logical
filters, and input version for resume. Per-Object completion remains canonical:
resume first applies the event tail and reconciles deterministic operation keys.
A destination file left by a crash between no-replace publication and event
append is adopted only after a successful full-file hash against the selected
Object; otherwise it is an ordinary collision and is never overwritten.

The complete-scan finalization transaction is the intentional exception to
ordinary batch-sized writes. Before appending `scan_completed`, the command uses
candidate/coverage counts and SQLite page estimates for a free-space preflight.
The MVP release gate must successfully finalize at least 500,000 covered facts
and 500,000 missing candidates in one disposable fixture while recording elapsed
time, peak memory, database/WAL growth, and recovery after injected rollback. If
that floor cannot be met, implementation must use a finalized-generation
indirection before release; it may not expose chunked partial activation.

## Jobs

### Local background configuration

`local/background.json` is a versioned, machine-local operational file with
`enabled`, `paused`, and `max_items` fields. It is written by atomic replacement,
is not canonical history, is not projected into SQLite, and is not synchronized
between installations. Missing configuration means disabled with a bound of 100
Copy claims. Limits from 1 through 1,000 keep one-shot scheduler work bounded.

Background target selection queries current `present` Copy claims and the
applicable Collection policy's `max_observation_age_days`, then restricts reads
to active filesystem Locations whose confirmed Device check-in and revalidated
Archive Root mount both match. It orders null/oldest observations first and
chooses one stable active File representation per Copy claim. Selection does not
enumerate a Location directory. Successful reads refresh the existing Copy and
verification projections; failures use the existing corrupt/unknown lifecycle.

### `jobs`

Local-operational resumable work units:


### `operation_outcomes`

Canonically derived idempotency index for resumable outcomes:

```text
operation_key TEXT PRIMARY KEY
record_id TEXT NOT NULL
item_index INTEGER NOT NULL

WITHOUT ROWID
```

The key is a versioned hash of job ID, job type, immutable input version, item key,
outcome kind, and target identity. One item may intentionally produce several
facts, each with a distinct outcome kind/key. On resume, canonical tail
projection precedes queue reconciliation; a matching key marks the local item
outcome complete. Under the local origin writer lock, appending an already present
key is rejected. This closes the record-durable/queue-incomplete crash window
without a distributed transaction.

This table is deliberately a compact exact-key index rather than a second copy
of the job/outcome payload. `record_id` plus `item_index` navigates to canonical
evidence; origin identity and sequence join through `records`. Job type, item
key, outcome kind, and target remain in the immutable canonical item and their
query-serving domain projections. A `WITHOUT ROWID` table gives operation-key
lookups one B-tree rather than storing the same text primary key in both a table
and an automatic index.

## git-annex import

### `annex_imports`

```text

```

Source-specific keys live in `external_identities`; there is no second
authoritative object mapping table. One user-facing Location represents the
annex repository. Worktree representations and annex object-store paths are
stored as paths within that Location rather than requiring the user to register
two Locations for one repository.

An import validates that the device, root, and repository path agree. Automatically derived location IDs are collision-safe and do not rely only on collection plus directory basename.

The importer records every encountered category. Known but absent content creates external identity, file reference, path observation, and source-metadata availability facts as applicable. Unsupported content remains visible with an explicit state and summary; it is not counted as protected.

Import is the one-time source-metadata bootstrap for a repository Location.
Subsequent positive add and complete scan operations use the materialized annex
identity and representation facts plus direct filesystem observation; they do
not read Git history or run Git/git-annex. A direct observation updates the
local source availability row as `present`, `missing`, or `unknown`, resolves a
supported identity when verified bytes appear, and creates or refreshes the copy
claim at its Location-relative path. Complete-scan missing-candidate selection
associates annex object-store copies to Collection Files by
`external_identity_id`, because their physical paths intentionally differ from
logical paths.

Imports store locked copy paths as `.git/annex/objects/...` relative to the
Location.

Verified copy into an imported annex Location preserves a registered locked
worktree symlink. Its relative target must normalize beneath the Location's
`.git/annex/objects`, repeat the registered annex key in the expected terminal
path components, and resolve to the selected Object. Archive Ledger creates a
missing target with no-replace placement and records the CAS-relative Copy path;
ordinary and unregistered symlinks remain ignored or fail closed.

## Query and scale indexes

In addition to keys already named, the implementation must inspect query plans for:

- binary logical-path prefix and exact lookup, with display text returned separately;
- object/external identity to all file references;
- object to current copy claims;
- location/device/site to copy claims;
- latest complete scan per location;
- stale resolved Objects grouped and deduplicated by Location and Device using
  effective positive-observation time;
- verification result and age;
- active policy violations by collection and reason;
- Collection-to-Location inventory membership and Location, Device, and Site
  file/present-byte/stale summary rollups;
- latest complete policy evaluation by policy, version, frontier, and validity time;
- tail application by `(origin_id, origin_seq)` against an accepted
  frontier, including batch lookup by `batch_id`.
- active Files whose `first_seen_record_id` joins to an origin sequence beyond
  a supplied causal frontier, ordered by lossless logical path;
- a temporary requested-File relation joined set-wise to active Files, present
  Copy claims, Locations, latest host mount observations, Devices, and Sites for
  bounded application access pages and attachment-plan coverage.

Indexes must be justified by these queries and the 500,000-file fixture. Redundant speculative indexes are avoided because they increase projection cost.

For stale-presence queries, a Copy claim's effective positive-observation time
is the newer of its own `last_seen_time_utc_ms` and the completion time of its
effective `last_complete_scan_id`. Only current `present` claims with resolved
Object identity enter stale-Object counts. The unfiltered report evaluates age
against every applicable active Collection policy and treats an Object as stale
when it exceeds at least one applicable `max_observation_age_days`; an explicit
command age overrides those policy thresholds for that query only. Counts use
`COUNT(DISTINCT object_id)` within each Location and Device. Missing, corrupt,
unknown, and unresolved external identities are separate categories.

List queries order by a documented immutable key after their user-facing sort
fields. A continuation token contains a version, normalized query/filter hash,
the SQLite applied frontier hash, projection generation, and last composite sort
key. A later command rejects the token with `stale_continuation` if the frontier,
generation, or query hash
differs. The MVP does not retain cross-process SQLite snapshots merely to keep an
old token alive.

## Projection invariants

The projector enforces:

- strict genesis/frontier/record/item version support;
- referenced registry entities exist;
- full-snapshot updates preserve identity fields;
- external identity resolution agrees with expected hashes and sizes;
- path bytes are lossless, relative to their declared root, and cannot escape it;
- active confirmed device fingerprints are unique;
- active confirmed Archive Root filesystem fingerprints are unique unless an
  explicit conflict has made them non-qualifying;
- every device-backed location agrees with its root's device, and every service
  location has a site;
- missing candidates affect current state only through an atomic, digest-checked
  complete scan activation;
- copy verification refers to the exact copy claim and observed path;
- copy identity replacements and verification invalidation/recovery follow the
  lifecycle table above;
- successful import hashing updates verification state;
- device/site/risk mappings resolve without duplicates;
- resumable operation keys identify at most one canonical outcome;
- checkpoint commit identity comes only from a verified post-commit observation;
- metadata protection requires a matching replica and resolved non-overlapping
  destination topology;
- every operation/item kind is explicitly classified as policy-input-relevant
  or irrelevant, and the relevant generation advances atomically with projection;
- closed/retired registry facts remain queryable historically;
- applied origin cursors and local generations update atomically with each transaction;
- an accepted frontier has the same Archive ID and genesis hash as the database,
  contains every previously accepted origin without regression, and proves each
  advanced origin through its signed immutable manifest chain;
- records are accepted only from a client enrolled at their causal
  base, with valid origin sequence/hash continuity and a valid closed-segment
  signature;
- batch chunk ranges are consecutive and within the configured item/byte bounds,
  and completion count/digest agrees with the exact ordered items;
- a record's causal frontier is satisfied before its effects project, while
  concurrent contradictions remain explicit rather than using apply order as a
  winner;
- protected non-commutative records name a current scoped coordination token;
- each changed origin cursor and its derived rows update atomically, and the
  applied frontier advances only after every included ready range projects.

Projector failures leave the SQLite cursor before the failing record and produce
a stable error. They never mutate canonical JSONL.

## Full-fsck table classification

`archive fsck --full` compares deterministic logical content at the live
database's captured `applied_frontier_hash`. A projection that is behind the
current canonical frontier is rebuilt from the historical Git commit containing
that exact frontier; being behind remains a separate currentness finding and is
not projection divergence.

The schema table classification is exhaustive at runtime. Adding or removing a
table without updating the classification makes full fsck fail as an incomplete
check instead of silently omitting state. The currently compared v2 projection
tables are:

- `archive_meta`, excluding database-local generation and last-verified-checkpoint keys;
- `records`, `projection_origins`, `clients`, `batch_runs`,
  `coordination_tokens`, and `fact_conflicts`;
- `sites`, `policies`, `collections`, `devices`, `device_site_history`,
  `archive_roots`, `locations`, `device_mounts`, `risk_domains`, and
  `entity_risk_domains`;
- `objects`, `object_hashes`, `external_identities`,
  `external_availability`, `file_refs`, `path_observations`, `copy_claims`, and
  `verification_results`;
- `scan_runs`, `scan_missing_candidates`, `scan_pending_completions`,
  `operation_outcomes`, `annex_imports`, and `annex_remotes`.

`jobs` and `job_items` are the only currently excluded tables. They contain
installation-local resumable work, including unfinished attempts that a clean
canonical rebuild must not reproduce. Exclusion does not make them canonical or
permit them to affect file-preservation truth.

Digests encode SQLite value types and bytes, order rows deterministically, and
include row counts. The disposable rebuild separately passes
`integrity_check` and `foreign_key_check` before comparison. Neither its database
nor any digest is installed into the live Archive.

## Portable snapshot rules

A portable snapshot is produced with SQLite's supported consistent-snapshot
mechanism into a new file, then scrubbed and checked before publication. It
deletes unfinished `jobs`/`job_items` and other machine-local operational rows;
credentials, client private keys, discovery configuration, and transient mount
availability are never stored in the database and therefore cannot transfer.
Deterministic policy caches may remain only when their policy-input frontier,
rule version, and `valid_until` envelope are still usable.

The snapshot is transferred out of band rather than committed as a binary Git
object. Its adjacent signed manifest binds the database BLAKE3 and byte length, Archive
ID, schema and projector versions, canonical Git commit, genesis hash, accepted
and applied frontier hashes, and creation time. Clone downloads into a temporary
path, verifies all bindings against the already verified canonical tree, opens
SQLite read-only for integrity/schema checks, and installs with no-replace or
atomic replacement only when no usable target database would be lost. Snapshot
failure never modifies canonical history and falls back to full replay.

## Retention

The default is to retain all derived rows. Optional SQLite pruning may later remove:

- old successful verification rows while keeping all failures and the newest success per copy;
- record-mirror payloads from a development projection while retaining required
  header/audit rows; current v2 projections do not duplicate them;
- finished local-operational job items;
- inert missing candidates belonging to a canonically partial, failed, or
  cancelled scan, after their summary remains reproducible from canonical records.

Pruning requires a verified independently replicated checkpoint beyond the pruned facts and must not affect rebuildability, current policy results, or audit links promised by the CLI.

## Scale expectation

At one million logical files with roughly three copies:

- file and object tables are on the order of one million rows;
- path and copy tables are on the order of several million rows;
- verification history grows with actual verification attempts;
- compliant files consume no `policy_status` rows, while one small complete
  evaluation envelope proves what their absence means;
- import, projection, scan, verification, and rebuild remain streaming and bounded-memory.

These are sizing expectations, not proof. The implementation plan's scale gate supplies measurements before release.
