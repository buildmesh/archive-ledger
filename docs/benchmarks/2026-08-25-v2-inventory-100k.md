# Version 2 inventory acceptance: 100,000 files

Date: 2026-08-25

Scope: the real v2 CLI, resumable filesystem inventory, bounded canonical batch
publication, incremental schema-6 projection, indexed Archive status, Git commit
behavior, verification, and replacement rebuild. The disposable fixture uses
100 directories containing 1,000 empty regular files each. Empty content makes
all logical Files share one Object, which deliberately stresses duplicate-content
risk evaluation while still creating 100,000 File, path, copy, verification, and
operation-outcome rows.

## Reproduce

Build the test first so compiler/linker memory is not attributed to the
application, then time the already-built test process:

```bash
cargo test --test v2_scale_100k --no-run
/usr/bin/time -v env ARCHIVE_LEDGER_V2_SCALE_FILES=100000 \
  cargo test --test v2_scale_100k -- \
  --ignored --nocapture --test-threads=1
```

Set `ARCHIVE_LEDGER_SCALE_KEEP=1` to retain the disposable Archive for independent
SQLite or CLI inspection. The test interrupts after 50,000 files and asserts that
the canonical Git commit count has not changed, resumes the same job, and requires
the completed 100,000-file logical operation to add exactly one Git commit.

The inventory batch contains 100,000 content observations plus job start/finish,

both item and byte limits; there is no per-file event file or commit. The SQLite
projection uses about 4.30 KiB per logical File in this deliberately index-heavy
fixture, versus roughly 16.5 KiB per File in the superseded unbatched baseline.
Raw canonical data uses about 1.23 KiB per File before Git packing.

## 100,000-observation synchronization delta

The retained disposable Archive was pushed to a local bare Git remote and cloned
with its current SQLite projection. The source then published another complete
100,000-file verification as one logical batch. The replica fetched the new Git
commit and incrementally applied the 111 new physical records without receiving
the source SQLite database.

| Stage | Elapsed | Maximum RSS | Swaps |
| --- | ---: | ---: | ---: |
| Source rescan, publish, and apply | 176.27 s | 114,816 KiB | 0 |
| Replica fetch, verify, and incremental apply | 171.02 s | 125,056 KiB | 0 |

The replica advanced one origin by 111 records. Independent checks returned
`PRAGMA integrity_check = ok`, 100,000 active File rows, 100,000 present copy
claims, 246 total canonical records, and identical accepted/applied frontier
hashes. This is the phase that previously exhausted the small test server.

## Layered fsck on the retained Archive

The same retained Archive was checked after the second 100,000-observation
batch. At that point canonical Git occupied 247,234,167 bytes and the live
projection occupied 642,764,800 bytes. The measured process was an already-built
debug CLI, so compiler memory is excluded.

| Check | Elapsed | Maximum RSS | Process swaps |
| --- | ---: | ---: | ---: |
| Routine Git/event/SQLite/cursor fsck | 54.97 s | 124,572 KiB | 0 |
| `fsck --full` disposable rebuild and logical comparison | 401.38 s | 124,728 KiB | 0 |

The full check passed rebuilt `integrity_check` and `foreign_key_check`, matched
every classified event-derived table, and left the selected rebuild directory
empty. This is bounded-memory evidence on the available 3.7 GiB host, not the
separate 500,000-File release-scale measurement. Regenerating the 500,000-file
fixture was deliberately not repeated after earlier host OOM reboots; that gate
should run once on a suitably provisioned runner rather than making swap the
normal execution strategy.

## Defects exposed and retained fixes

The first 100,000-file run exposed two concrete scale defects:

- The local resume index committed every seen path as a separate SQLite
  transaction. The retained implementation writes enumeration outcomes to the
  durable spool first and commits the local seen-path index as one transaction at
  the resume boundary. At 10,000 files, the interrupted half fell from 15.670 s to
  0.474 s. A crash before the ordered spool/index boundary rolls back and recovers
  from the spool.
- Risk status joined every logical File to every copy claim for the same
  deduplicated Object. Ten thousand identical files attempted a 100-million-row
  intermediate and failed with SQLite `database or disk is full`; 100,000 would
  have implied ten billion rows. Coverage is now aggregated once per Object, then
  the concise status totals are computed directly in SQL. Cold 100,000-file
  Archive status dropped from 13.0 s to 0.37 s. Detailed risk findings retain a
  deterministic per-File path only when explicitly requested.
- Full and incremental v2 verification read an entire signed segment and retained
  every decoded JSON item. The append fast path did the same for the previous
  segment, so routine scans and replica projection scaled toward hundreds of
  megabytes of live decoded state. Signed segments are now hashed with a fixed
  64 KiB buffer and parsed one record at a time, with rolling origin-chain and
  batch-digest state. Projection consumes each completely authenticated segment
  immediately. At 10,000 Files, a repeat `collection add` fell from 162,148 KiB
  to 27,184 KiB RSS; the 100,000-observation replica apply used 125,056 KiB.

## Interpretation

This gate demonstrates the intended single-user hundreds-of-thousands scale for
one large logical inventory operation without requiring all paths or items in
memory, without per-file Git history, and with a bounded-memory incremental sync
path. It is not a claim that all possible
workloads take the same time: non-empty files add physical read and hashing cost,
multiple Objects change compression and table mix, and storage hardware matters.
The five-second automated status ceiling is a regression bound, not a product
latency promise.
