# Guarded 200k inventory-only rebuild experiment

Tracked by **al-j5k**, following the [100k production experiment](2026-09-24-rebuild-production.md#subsequent-guarded-100000-entry-run).
The user requested another doubling with tiny fixture entries because the
original slow collection initialization used `--inventory-only`.

## Workload and controls

The fixture has 200,000 distinct deterministic annex keys and locked symlinks.
Each symlink target is 195 bytes; no referenced media contents exist. The key's
nominal 1,024-byte size is metadata, not allocated file content. This preserves
the earlier benchmark's metadata projection workload. It does not test hashing
or reading photo/video contents. Filesystem and Git metadata still require I/O,
and filesystem allocation exceeds the tiny symlink payloads.

Production source is unchanged at `c12273d` (runtime implementation `1d258b9`).
The locked, offline release build used one build job, no debug information,
and no incremental compilation. Its binary SHA-256 exactly matches the 100k
binary: `647bcc0da5bac0d052449ee2e2fc28796e47df690a8cbe04dbf98aabb56e1975`.
Rebuild uses the same 64-record transactions, 64 MiB cache target, cached
statements, deferred reporting indexes, and normal FULL/DELETE durability.

Initial host checks showed approximately 1.25 GiB available RAM, almost no free
swap, zero memory PSI, and 6.75 GiB free disk. The host is the same shared ext4 /
virtual-NVMe runner, not the user's spinning hard drive. Each workload phase
ran separately with:

- 896 MiB hard memory ceiling, 768 MiB soft limit, and no additional swap.
- Early stop at 832 MiB actual scope charge or below 384 MiB available host RAM.
- Stop after five seconds of memory PSI some avg10 above 5% or full above 2%.
- At least 1 GiB free disk; one-core affinity, reduced CPU priority, idle I/O priority.
- Preflight requiring 1,200 MiB available RAM and memory PSI some/full avg10
  at or below 2%/1%; the launcher waited when these conditions were not met.
  Later launches required 1,240 MiB to leave room for wrapper startup.

The build succeeded in 301.88 scope seconds. Fixture generation was split into
20 independently guarded batches of 10,000, with one final quiet Git commit.
All batches completed, each below 198 MiB peak scope charge. The committed tree
and index each contained exactly 200,000 entries; every committed entry had Git
symlink mode. This changed only fixture setup, not the measured application.

## Setup interruptions and recovery

The initial inventory-only import stopped on memory PSI after 234.76 scope
seconds, with approximately 198 MB of checkpointed metadata spool. Its scope
peaked at 523.7 MiB with no soft-limit events. The supported `job resume
job_benchmark` command reused the checkpoint, then stopped on PSI after another
170.43 scope seconds with approximately 255 MB spooled. Its peak was 620.9 MiB,
again without soft-limit events. These host-pressure stops were not exhaustion
of the scope's memory allowance. Neither recorded a hard-limit event or OOM.

A second job resume completed the approximately 387 MB spool but stopped on PSI
after 367.78 scope seconds during canonical publication. The working frontier
had advanced, while Git HEAD still referenced the previous frontier. Exactly
four paths were pending: the frontier HEAD, one event segment, its manifest,
and the new frontier document. `archive events verify` passed: 398 signed
records, nine segments, and a complete inventory batch with 200,004 items.

This reproduced a separate publication-recovery gap, tracked as **al-say**.
The existing resume path can apply a working frontier without completing its
missing Git commit; a dedicated supported recovery path was not found. For this
disposable fixture only, the exact four verified files were staged and committed
using the existing `commit_canonical_tree` identity/message. No signed event
contents changed. Working and committed frontier HEAD then matched and Git was
clean. That recovery succeeded in a separate 7.11-second scope after an initial
headroom preflight declined to launch. It was manual fixture recovery, not a
successful unattended product recovery test or a recommended user workflow.

The now-committed history was projected using ordinary incremental `db apply`
to establish an independent reference. That command completed in 656.23 seconds
(656.54 for its scope), used 151.86 CPU seconds and 16.5 MiB peak CLI RSS,
and recorded 18,527.72 MB of writes. The resulting database was 671,125,504
bytes. This measures ordinary apply onto the existing small registry projection,
not a baseline full rebuild. No additional swap was used. Interrupted import, source rechecks,
manual publication recovery, and subsequent apply are separate setup work;
none constitute an uninterrupted 200k collection-init timing.

Two reference-integrity attempts using the benchmark helper's default SQLite
read cache stopped on memory PSI after 89.86 and 31.62 seconds. Their scope
peaks were 530.7 and 307.2 MiB, below the soft limit. The second stop coincided
with approximately 24% full memory PSI and 79% full I/O PSI; it is not treated
as a failed integrity assertion.

An additional reference-integrity attempt with a 64 MiB read cache and a longer
quiet-period preflight also stopped on PSI after 47.33 seconds. The redundant
upfront integrity pass was then replaced with counts, completed-batch, and
frontier checks; the production rebuild still performs its own full integrity
and foreign-key checks. Read-only diagnostic connections use a 64 MiB cache
target per database, outside the timed CLI. The source symlink fixture and
redundant import spool were removed after complete counts and publication were
verified; canonical history and the independent projection were preserved.

## Successful rebuild

The first rebuild attempt stopped on PSI after 125.05 scope seconds. Its
unfinished output retained schema version zero; only that disposable partial
output and its sidecars were removed before retrying. The second attempt
completed with the same binary, database settings, and resource controls.

| Entries | Rebuild seconds | CPU seconds | CLI peak RSS, MiB | Recorded writes, MB |
| ---: | ---: | ---: | ---: | ---: |
| 50,000, earlier observation | 21.36 | 17.90 | 81.3 | 208.40 |
| 100,000, earlier observation | 45.11 | 34.31 | 84.8 | 679.85 |
| 200,000 | 178.73 | 84.44 | 93.3 | 2,321.96 |

The successful command includes replay, deferred index construction, validation,
and installation. Its resulting database is 666,390,528 bytes. Sampled CLI swap
was zero. The enclosing scope lasted 179.05 seconds, peaked at 768.15 MiB actual
charge including filesystem cache and 131.61 MiB summed process RSS, and retained
at least 1,114.88 MiB available host RAM. It recorded 7,688 soft-limit events,
zero hard-limit/OOM events, and unchanged global OOM-kill counts at zero.
Memory PSI some/full avg10 peaked at 1.28%/1.06%, below the stop thresholds.

Doubling from 100k took 3.96 times the elapsed time, 2.46 times the CPU, and
3.42 times the recorded writes. CLI RSS increased only 8.6 MiB. However,
accounted reads rose from 3.25 MB to 2,502.81 MB, and the scope reached its soft
limit; the 100k scope peaked at 478.8 MiB without soft-limit events. Cache
reclaim and shared-host I/O conditions are plausible contributors to the extra
elapsed time. These observations do not isolate algorithmic scaling or predict
HDD runtime. Earlier work warmed some filesystem caches, but this was not an
all-in-RAM workload or a controlled cold-cache comparison.

The measured write growth remains a useful optimization target. Ordinary
initial apply also remains substantially more expensive: 656.23 seconds and
18.53 GB of writes in this fixture. The tiny inputs confirm that media-content
reading is unnecessary to produce substantial metadata projection traffic.
No further product tuning or larger fixture was attempted in this run.

## Verification

The successful production rebuild passed its full SQLite integrity check,
foreign-key check, and canonical-frontier validation before setting schema
version six. A monolithic external comparison subsequently stopped on memory
PSI after 103.13 seconds, so the remaining exact comparisons were split by table
with checkpoints. This removed repeated integrity scans from the external
comparison; no separate completed full integrity scan of the reference is
claimed.

All 31 derived tables and the full schema matched the independent incremental
reference. Checks used equal row counts and bidirectional SQL `EXCEPT`, with
the same exclusions as the earlier benchmark: installation-local `jobs` and
`job_items`, plus `projection_generation`, `policy_input_generation`,
`last_verified_checkpoint_id`, and `last_verified_checkpoint_frontier_hash`.
Each checkpoint records database identity, size, and modification time; the
aggregate check confirmed all compared unchanged inputs. The five principal
inventory tables each contain exactly 200,000 rows; no objects or verification
results were created. Canonical Git HEAD remained
`720858235874a84ff20a22f5b7876caee2e0deee`.

Routine `archive --json fsck` did **not complete**. Its first attempt stopped on
memory PSI after 139.54 scope seconds, peaking at 767.99 MiB with 411 soft-limit
events. After waiting for headroom, the second attempt stopped on PSI after
92.14 seconds, peaking at 636.52 MiB with no soft-limit events. Neither returned
a completed report or an integrity assertion failure. Further retries were
stopped; this remains a verification limitation despite the successful rebuild
integrity checks and exact comparison. `fsck --full` was not run.

All 74 completed guard reports, including declined preflights and interrupted
phases, were audited: no hard-limit, OOM, or OOM-kill events; sampled global
OOM-kill counters remained zero. Final read-only checks confirmed canonical Git
was clean and both compared database files were unchanged. No benchmark
processes remain running. These results establish a successful guarded rebuild,
not a successful uninterrupted collection initialization or unrestricted 200k
run. Production source did not change, so unit tests were not rerun; the
release build, measured reconstruction, and exact comparison are this run's
validation. The report passed `git diff --check`.

## Reproduction and retained evidence

On a runner with adequate headroom, the existing harness accepts this size:

```sh
python3 scripts/benchmark-annex-inventory.py \
  --binary /absolute/path/to/archive \
  --work-dir /absolute/path/to/owned-staging --sizes 200000
```

Build from `c12273d` with `cargo build --release --locked`, one build job, and
the release settings above. The work directory must exist and its size
subdirectory must be new. This run used task-local wrappers to split fixture
creation into 10k chunks and application/validation into independently guarded
phases. Do not run the unsupervised command on this shared host: use the active
memory/PSI watchdog and limits described above. Rebuild comparisons exclude
fixture creation, initial apply, pauses, backup, and external verification.

Task-owned staging is intentionally retained at
`/home/ubuntu/tmp/archive-ledger-al-j5k-200k-5p5ntku5`, owned by Codex for
**al-j5k**. It contains the disposable canonical history, independent incremental
reference, rebuilt database, identical release binary, wrappers, and raw
telemetry for the write-amplification follow-up. The source symlinks, redundant
import spool, and build target were removed. Beads and `owner.json` record the
removal condition: delete this exact owned root after the follow-up comparisons
are recorded or the fixture is explicitly no longer needed. No real archive
data is present.
