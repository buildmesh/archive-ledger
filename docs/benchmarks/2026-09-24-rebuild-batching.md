# Rebuild batching experiments

Tracked by **al-j5k**, following the [5k–50k baseline](2026-09-24-annex-inventory-rebuild-50k.md).
The reported 800,000-file desktop import used a spinning hard drive for everything.
This investigation tests bounded RAM buffering and fewer database writes on the
same virtual-NVMe runner as the baseline; it does not measure HDD recovery time.

## Approach

The production source remains unchanged. An isolated copy of revision `a408264`
was built with the [unapplied experiment patch](2026-09-24-rebuild-experiment.patch).
The experimental settings affect only new-database construction and use private
flags; they are not supported product settings.

The candidates are:

- **Group transactions:** stream up to 16 canonical records into each transaction
  instead of committing each record. Records remain in canonical order and are
  decoded one at a time. Existing record limits imply at most 16 MiB of canonical
  input per group, not 16 MiB of total process memory or database changes. A scan
  completion can legitimately update many more rows.
- **Bounded page cache:** give the replay connection a 64 MiB SQLite page-cache
  target, allowing changed pages to accumulate between commits. This is a cache
  target, not a hard RSS ceiling. It is independent of archive size.
- **Defer selected indexes:** build 26 explicitly selected nonunique indexes after
  replay. Keep every primary key and uniqueness constraint throughout replay,
  plus the five nonunique indexes needed by complete-scan replay queries. Restore
  exact index definitions before integrity checks or installation.
- **WAL:** compare the combined changes with WAL and FULL synchronization, then
  checkpoint and return to DELETE journal mode before installation. All other
  variants retain the normal DELETE journal and FULL synchronization.

This uses SQLite's own page buffering rather than collecting the entire archive
in application RAM. Larger transactions can amortize repeated writes of the same
pages; increasing cache size alone cannot avoid commit-time persistence. SQLite
documents the cache target and mid-transaction spilling in its
[PRAGMA reference](https://www.sqlite.org/pragma.html#pragma_cache_size).

## 10,000-entry comparison

Every variant rebuilds exactly the same canonical history generated by the
unchanged release CLI. Timings include the full rebuild, deferred-index creation,
validation, and installation. External equivalence checks happen after timing.

| Variant | Seconds | Recorded writes, MB | Peak sampled RSS, MiB |
| --- | ---: | ---: | ---: |
| Default | 9.08 | 217.9 | 16.9 |
| Cache 64 MiB | 8.85 | 217.5 | 48.3 |
| Group 16 records | 7.35 | 44.8 | 17.0 |
| Deferred indexes | 8.06 | 194.6 | 16.8 |
| Cache + grouping | 8.20 | 44.8 | 48.0 |
| Cache + grouping + deferred indexes | 6.38 | 44.4 | 46.1 |
| Cache + grouping + deferred indexes + WAL | 5.57 | 77.2 | 45.6 |
| Default repeated | 9.40 | 217.9 | 17.0 |

Grouping reduced recorded write traffic by approximately 79% at this size.
Cache alone did little. The fastest elapsed time used WAL, but wrote more bytes
than the equivalent DELETE configuration. Bytes alone do not measure seek cost
or establish which configuration will perform best on a spinning disk.

## 50,000-entry comparison

The unchanged release CLI rebuilt the new fixture in 102.92 seconds, consistent
with the earlier 107.47-second baseline. Its inventory import took 119.63 seconds.
The following prototypes reconstructed that same canonical history:

| Variant | Seconds | Recorded writes, MB | Peak sampled RSS, MiB |
| --- | ---: | ---: | ---: |
| Original CLI baseline | 102.92 | 2,903.3 | 17.8 |
| Cache + grouping | 41.97 | 469.6 | 84.2 |
| Cache + grouping + deferred indexes | 35.05 | 435.1 | 85.0 |
| Cache + grouping + deferred indexes + WAL | 86.39 | 648.4 | 84.0 |
| Default repeated | 103.90 | 2,905.8 | 16.8 |
| Cache + grouping + deferred indexes repeated | 41.19 | 435.2 | 85.7 |

The combined DELETE-journal candidate was approximately **2.5–2.9 times faster** and
recorded **85% fewer write bytes** than the original CLI. It consumed 28.83 CPU
seconds of 35.05 elapsed seconds. That makes reducing repeated SQL preparation
a useful next experiment after reducing I/O. The resulting database is larger
than the 64 MiB cache, so this is not a whole-database-in-RAM result.
All sampled benchmark processes reported zero swap use.
The repeated candidate's write volume was essentially unchanged; elapsed time
varied from 35.05 to 41.19 seconds, so a single timing should not be overinterpreted.

WAL's small-fixture advantage did not persist: at 50k it took 86.39 seconds and
recorded 515.7 MB of reads. Cache/checkpoint effects and shared-host variability
need further isolation; these observations do not justify adopting WAL for this
path. The prototype closes its replay connection before index creation, so WAL
can checkpoint at that boundary as well as during finalization.

The combined DELETE candidate grew from 6.38 seconds at 10k to 35.05 seconds at
50k (5.5 times the time for five times the entries), compared with approximately
11 times for the default. This is a substantial improvement over the baseline's
scaling, but does not establish linear behavior to 800k. A simple 16-times
extrapolation of the 35–41-second observations would be about 9–11 minutes **on this runner**;
it is not an HDD recovery guarantee. Neither 100k nor 800k was run.

## Verification

All seven 20-entry smoke variants, eight 10k comparisons, and five 50k
comparisons (including the candidate repeat) passed exact user-table and schema
comparison against the unchanged CLI's rebuild. SQLite integrity and foreign-key
checks passed; each final database used DELETE mode with no WAL/SHM sidecars.
Canonical HEAD stayed unchanged.

A separate 50k interruption test copied the known-good baseline database to a
disposable target, started the combined DELETE candidate, and sent SIGKILL after
the replacement's temporary files exceeded 8 MiB. The existing target remained
byte-for-byte unchanged. Retrying succeeded and reproduced every baseline table,
with clean integrity and foreign-key checks. This tests interruption during
construction, not every possible power-loss or final-installation boundary.

The seven existing `v2_projection::tests` passed in release mode with
`ARCHIVE_REBUILD_EXPERIMENT=cache64,group16,defer`. They cover reconstruction,
incremental resume, multiple origins, conflicting identities, schema rejection,
and item defaults. This was the focused projection suite, not the full test suite.
The retained patch was separately applied to a clean copy and confirmed to
reproduce the exact benchmarked source.

## Interpretation and remaining work

The experiment preserves canonical ordering, uniqueness, rollback, and FULL
durability. It does not sort or collapse events, disable constraints, disable
journaling, or build an archive-sized in-memory database. SQLite warns that
disabling its journal compromises rollback and crash recovery; that tradeoff was
not needed for these experiments. See
[SQLite atomic commit](https://www.sqlite.org/atomiccommit.html).

Before promoting a candidate into production, validate mixed histories including
large completed scans, reimports, resolved identities and conflicts. Indexes can
also serve foreign-key checks; the fresh-inventory result is not evidence that
all other workloads improve. Review failure cleanup and checkpoint results,
including failures during index creation and final installation.

Repeated SQL preparation on the annex projection path is another concrete CPU
optimization opportunity. The current v2 path repeatedly executes the same SQL
without cached prepared statements. That was inspected but not changed in this
experiment. Avoid adding parallel writers before eliminating repeated work:
replay ordering and a single SQLite writer make independent write workers a
poor first step.

The recommended implementation direction is a rebuild-only bulk mode using
bounded grouped transactions and page buffering, followed by selected index
creation. Share the existing projection rules rather than introducing a second
event interpreter. Keep incremental apply's current recovery behavior until it
has its own measured and tested change. Reuse prepared statements next, then
retest at 50k and consider 100k plus a real disposable HDD run.

## Reproduce

Use Linux, Python 3.9+, Git, Rust, and a new task-owned staging directory. Both
binaries use release mode, one build job, no debug information, and no incremental
compilation. The shared runner has two virtual CPUs, approximately 3.8 GiB RAM,
and ext4 on virtual NVMe; measurements are sequential with warm filesystem caches.
They are individual observations, not statistically controlled distributions.
`/proc/PID/io` reports process-accounted writes, not physical device seek counts.

From the repository, preserve a baseline binary, then apply the research patch
only to an isolated copy:

```bash
benchmark_root=$(mktemp -d /home/ubuntu/tmp/archive-ledger-al-j5k-XXXXXX)
mkdir "$benchmark_root/source"
git archive a408264 | tar -x -C "$benchmark_root/source"
export CARGO_TARGET_DIR="$benchmark_root/target"
export CARGO_BUILD_JOBS=1 CARGO_PROFILE_RELEASE_DEBUG=0 CARGO_INCREMENTAL=0
cargo build --release --locked --manifest-path "$benchmark_root/source/Cargo.toml"
cp "$CARGO_TARGET_DIR/release/archive" "$benchmark_root/archive-baseline"
patch -d "$benchmark_root/source" -p1 < docs/benchmarks/2026-09-24-rebuild-experiment.patch
cargo build --release --locked --manifest-path "$benchmark_root/source/Cargo.toml"
python3 scripts/benchmark-annex-inventory.py \
  --binary "$benchmark_root/archive-baseline" --work-dir "$benchmark_root" \
  --sizes 20 10000 50000
python3 scripts/benchmark-rebuild-experiment.py \
  --binary "$CARGO_TARGET_DIR/release/archive" \
  --fixture "$benchmark_root/annex-10000" --output "$benchmark_root/compare-10k" \
  --variants default cache64 group16 defer cache64,group16 \
    cache64,group16,defer cache64,group16,defer,wal default-repeat
python3 scripts/benchmark-rebuild-experiment.py \
  --binary "$CARGO_TARGET_DIR/release/archive" \
  --fixture "$benchmark_root/annex-50000" --output "$benchmark_root/compare-50k" \
  --variants cache64,group16 cache64,group16,defer \
    cache64,group16,defer,wal default-repeat
```

The comparison harness verifies every user table in both directions using SQL
`EXCEPT`, compares counts and exact schema definitions, checks SQLite integrity
and foreign keys, and confirms final DELETE mode without WAL/SHM sidecars. It also
checks canonical HEAD remains unchanged. Preserve concise results, then remove
only the exact task-owned staging directory. No real archive is required.
